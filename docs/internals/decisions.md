# shoppinglist: Decisions

Rationale and rejected alternatives for the design in [`design.md`](design.md). The spec describes the system **as it is to be built**; this file records **why**, and **what we chose against**. What each tagged release shipped is in [`CHANGELOG.md`](../../CHANGELOG.md). Spec sections cite these as `[D-xx]`.

An entry says what holds now: the rule, why, and what was chosen against. A decision replaced completely is deleted, and what cited it cites what replaced it; one replaced in part keeps what still holds and names what replaced the rest. Numbers are never reused, so the log has gaps.

## Decision log

<a id="D-54"></a>**[D-54] The frontend UI layer is shadcn-svelte on Tailwind v4 (2026-08).** The app's primitives (sheets, dialogs, buttons, single-select groups) come from shadcn-svelte on bits-ui, with bundled CSS in place of hand-written CSS. The tokens use shadcn's names (`--background`, `--primary`, `--destructive`, `--border`), the `--cat-*` tokens are custom `@theme inline` entries, and dark mode is `.dark` + `@custom-variant dark` with mode-watcher for the theme toggle. The look stays the app's green.

**Constraints:**
- AddBar uses the **bits-ui Combobox primitive directly**, not shadcn's Popover+Command. An inline free-text input is a different shape, and the ✕ suppression interaction stays custom under the ARIA rule that an option must not hold focusable children.
- Toasts go through Sonner behind a **dismiss-before-show wrapper**, so [§9.1]'s one-slot newest-wins toasts never stack.
- `categoryStyle()` is the only writer of `--c`.

*Rejected: bits-ui alone* (headless: it leaves all the CSS, which is most of the gain). *Rejected: Skeleton* (a second theming layer on top of Tailwind, and no drag-to-dismiss sheet or single-slot toast). *Rejected: Flowbite* (not runes-native or Tailwind v4-ready where this repo needs it). *Rejected: hand-rolling shadcn's primitives on bits-ui* (gives up the bundled CSS, which is what this decision is for). ([§9])

<a id="D-55"></a>**[D-55] Sign-out on this device wipes the account's local data (2026-08).** Beside „Überall abmelden", Settings has „Auf diesem Gerät abmelden" ([D-214]), so a shared device can change hands without revoking every session: local-only, it revokes nothing and works offline.

**`logout()` ends the session generation first, so nothing in flight writes behind it ([D-109]),** clears the auth store and the service-worker photo cache ([D-21]), then awaits `wipeLocalAccountData()`. The Dexie mirror is not account-scoped and the `pending_ops` outbox has no account column, so without the wipe the next account inherits the lists and co-members' nicknames, and the previous account's ops drain under the new token, come back `denied` and stick beyond UI repair. One transaction clears every list-data table (shadows and outbox included), `scanned_products` and the account-bound `meta` keys ([D-148]). Kept: the seeded vocabulary, the same for every account and needed offline, and the device preferences. A wipe that fails is reported, and the whole database is deleted and the page reloaded instead: a sign-out never leaves the account's data behind. With edits queued it warns first („Trotzdem abmelden"). „Überall abmelden" and account deletion await `logout()`, so "signed out" never precedes the wipe.

*Rejected:* account-scoping the tables (a schema-wide column for a one-account device, breaking the [§8] outbox contract); filtering the outbox at drain time (no owner column, auth already cleared). ([§4.5], [§5.6], [§8], [D-21], [D-109], [D-148], [D-214])

<a id="D-56"></a>**[D-56] Primary controls have a 44px effective touch target (2026-08).** Every control rendering `[data-slot="button"]` has a 44px *effective* target (WCAG 2.5.5). The painted size may be smaller and reach 44 through a `::after` hit-area inset, as the sync-status chip does ([§12.1]). Everything else keeps the 24px WCAG 2.5.8 floor. `e2e/tests/a11y-manual.spec.ts` checks both floors. So the vendored shadcn-svelte button scale ([D-54]) is deliberately not taken as shipped: `sm` is 36px painted, 44 effective; `icon` is 40px painted, 48 effective. A refresh of the vendored components must not reset this scale. Its two text heights were replaced by [D-312]: one 44px `default`, `lg` gone. Menu entries (the list card's ⋮ menu, the sort menu, every shared `ui/dropdown-menu` item) are 44px painted.

<a id="D-57"></a>**[D-57] No member avatars (2026-08).** The share sheet's roster ([§7.1]) shows nickname, "du" badge and join date only. An avatar was never specified: [§7.4]'s roster route returns exactly `[{account, nickname, joined}]`, `accounts` has no image field, and `img-src 'self'` ([D-21]) rules out remote avatar services. A synthesised colour-and-initials circle carries nothing the nickname beside it does not, and its white-on-hash-colour fill failed contrast in both themes. Do not add one: an avatar needs an upload path, a synced field and a privacy review first. ([§7.1], [§7.4], [D-21])

### Identity & authentication

<a id="D-01"></a>**[D-01] Passwordless, anonymous, credential-agnostic identity.** An account is a stable ID that *has* one or more credentials; it never *is* a passkey or an email. This is what makes "anonymous passkey now, optional email later, multiple passkeys" work with no migration. No PII at signup. ([§4])

<a id="D-02"></a>**[D-02] Discoverable passkeys are mandatory.** Accounts have random handles, so the user cannot type a username. Registration requires resident/discoverable keys and login uses discoverable login. ([§5.3])

<a id="D-03"></a>**[D-03] Ceremony session data lives in server memory, not in a signed cookie or a database row.** A ceremony spans two requests; the one-time challenge must survive between them. The instance is one process, as its rate limits already assume ([D-307]), so `internal/webauthn` keeps each session in a locked map in PocketBase's per-app `app.Store()`, keyed by browser id and type, for five minutes, and the finish takes it under the lock. A restart drops the open ceremonies, and the person taps again. *Rejected:* a signed cookie (installed-PWA cookie quirks, flaky in iOS standalone); a `webauthn_sessions` collection (a table, a migration and a ten-minute sweep for state that lives five minutes). ([§5.5])

<a id="D-04"></a>**[D-04] 90-day sliding token; revoke = per-account token-key rotation.** `authRefresh()` on every start/reconnect slides the window, so "save to home screen, stay logged in for months" works while bounding a stolen token. Shared-device exposure is accepted for a shopping list. ([§5.6])

<a id="D-05"></a>**[D-05] Offline gate = "authenticated at least once, ever."** Local Dexie data is readable/writable with no valid token; the token gates *syncing only*. Expired-on-reconnect ⇒ one-tap passkey re-auth (a WebAuthn assertion cannot be silent), which never blocks local use and preserves queued edits. Accepted: the app is fully usable offline in a state where we cannot currently prove who the user is; we trust the local device. ([§5.8])

<a id="D-32"></a>**[D-32] Account lifecycle: deletion leaves every list first, self-update is an allowlist, attribution does not cascade.** (a) **Account deletion = "leave every list, then delete"**: a dedicated route deletes the caller's memberships one by one through the normal delete pipeline so the last-one-out cascade fires per list (solo lists die; shared lists and the items the leaver added survive), then credentials, then the account (the route passes the [§5.4] last-credential guard with a request-scoped context value under an unexported key, given to `DeleteWithContext`, so every other delete still runs the guard; *rejected:* a package-level flag, which interleaving requests break, and a raw delete that skips hooks), never through PocketBase's implicit relation cascade, so hook ordering is guaranteed. The order is also required: `memberships.account` is a required, non-cascading relation, and PocketBase refuses to delete a record a required reference still points at. (b) The `accounts` self-update rule is an **allowlist** on the record API (`nickname` + suggestion suppression): PocketBase's own form refuses `email` and `verified` without manage access and keeps the hidden `tokenKey`, and a request hook refuses `handle`, since otherwise any user could rewrite their identity field or squat an email address, bypassing verification. A request hook, so the server's own saves (the token-key rotation, the OIDC link, PocketBase's OAuth2 verify) pass without a bypass; *rejected:* a model hook, which needed a context bypass for each of them. (c) `items.modified_by` and `invites.created_by` are **non-cascading relations**, because a cascading `modified_by` would delete every item a deleted account ever touched. PocketBase empties a non-cascading relation when its target is deleted, so the client shows "someone" for an **empty** `modified_by`, not for a lookup that failed. ([§4.5], [§6.6], [§6.8], [§11])

<a id="D-262"></a>**[D-262] The foot of settings shows a short code for the account (2026-10).** One person can hold two accounts with the same nickname, one from a passkey and one an OIDC sign-in created ([D-76] never merges them by name or address), and a re-auth that answers "a different account" needs something that tells them apart. Settings' foot shows „Konto K7Q2“ beside the version: 20 bits of the account id's FNV-1a hash in four Crockford base32 characters, derived on the device, so nothing is stored or fetched, and the same on every device signed in to the account. Two accounts of one person share a code with odds of about one in a million. It is a label, not a secret. *Rejected: the code in the passkey's label in the password manager, and naming both accounts in the re-auth's refusal.* Both show more technical detail than a person signing in needs, and the refusal would name another account to whoever holds this device. *Rejected: a colour or an identicon.* Neither can be read out or compared in text. *Rejected: the handle.* OIDC-born accounts have none ([§6.1]). ([§12], [D-76], [D-181])

<a id="D-307"></a>**[D-307] The app's routes have their own rate limiter beside PocketBase's (2026-10).** Every custom route's budget is in `internal/security/ratelimit.go` ([§10]), in memory; PocketBase's `settings.RateLimits` stays on as the catch-all for the rest. Its rules cannot hold ours: a rule's label is one concrete path or one prefix ending in `/`, so `/api/lists/{listId}/clone` has none, and the two passkey begin routes share a budget only under `/api/passkey/`, finish routes included, since only the first matching rule counts a request; it keys on the whole address, where ours counts an IPv6 client by its /64; and its rules are settings an operator edits in the dashboard, so a budget the security model counts on could be loosened unseen. *Rejected: PocketBase's rules alone,* for those reasons. ([§10])

<a id="D-309"></a>**[D-309] Deleting the account wants a sign-in from the last five minutes (2026-10).** Otherwise a token copied off a device, good for 90 days and refreshable ([D-04]), could end an account and its solo lists for good. Every sign-in's token carries when that sign-in happened (`auth_time`, OIDC's name for it), stamped in PocketBase's auth-response hook for every method (passkey, OIDC, demo start); auth-refresh mints its token without it. `POST /api/account/delete` refuses (403) a token without one from the last five minutes. The client signs in again as the confirmation is accepted, with the re-auth it already has ([D-76]): the account's passkey where this device can use one, else its linked OIDC login, whose provider sign-in counts the same. A dismissed prompt deletes nothing and says so. An account with neither login, as every demo account is ([D-234]), has nothing to sign in with and is deleted on its token; a login the instance switched off counts as none, the same rule as the last-passkey guard and the unlink ([D-76]). Only the delete asks: nothing else a token does is beyond undoing with the passkey. *Rejected:* a passkey assertion sent with the delete (a second verifier beside the login's, which an OIDC-only account still could not give); the token's issue time read off its expiry (auth-refresh renews it, so a stolen token refreshes into a fresh one). ([§4.5], [D-04], [D-32], [D-76], [D-234])

### Sharing & membership

<a id="D-06"></a>**[D-06] No owner; all members equal; no eviction.** Any member can edit, invite, see the roster, and leave. **Rejected:** owner/roles, kept out of v1 for simplicity. **Accepted tradeoff:** no one can evict a bad actor; the only remedy is other members leaving. Fine for lists shared among people who know each other. ([§7])

<a id="D-07"></a>**[D-07] Leave = hard delete of the membership row (memberships are not tombstoned).** The leaver's own device treats the leave as authoritative, so there's no offline-replay resurrection risk (the risk tombstones solve for items). Makes the last-one-out cascade a natural delete hook and keeps every rule "row exists ⇔ access exists." ([§7.2])

<a id="D-08"></a>**[D-08] Lists: created by route with a server-minted id, one name for every member, visible membership, every other id and capped column bounded (2026-07).**
- **A list is created by route and deleted by cascade, never carried in an op.** `lists` has no `deleted_at` and no client create or delete rule: create, clone and import make it in one transaction with the caller's membership ([§7.5]), and the last member's departure cascades it ([§7.3]). The op union has no `lists` slot (push answers `bad_collection`).
- **A list has one name, `lists.name`**, so a notice can name it in words every member recognises. Any member renames it by a direct update under `lists.UpdateRule`, a membership rule on a row whose only own column is `name`, so the rule is the allowlist; `listUpdateGuard` refuses a blank name or one over the contract's 200 bytes, as the three routes do. A rename reaches co-members on the next digest ([D-28]); concurrent renames are last-write-wins. The [D-72] backup keeps its `display_name` key for compatibility.
- **Membership is visible, not editable.** `memberships` has no name and no update rule, and a member deletes only their own row ([§7.2]). Co-members see who is on a list through the roster route alone ([§7.4]); `memberships` reads stay own-rows-only.
- **List ids are server-minted.** The [§7.5] routes write with `SaveNoValidate`, skipping PocketBase's field validation, so they ignore any body `id`, and PocketBase mints every id, copied rows included, from `crypto/rand`. Ids ride into every co-member's snapshot and digest, and the routes are online-only, so nothing needs a client list id. Removing the input beats validating it, as with invite tokens ([D-31]).
- **Item and category ids stay client-minted, and bounded.** They exist in Dexie and the outbox before the server sees them, and [D-42] makes a re-delivered create idempotent. Push checks `^[A-Za-z0-9_-]{8,64}$` on create (`bad_record_id`): a bound, not a format.
- **`list_categories.slug` is server-owned on every path.** Push refuses it. Import, whose file passes between people, accepts only `category_templates` slugs, each at most once, as in a genuine export, so a template-copied row keeps its link while a crafted backup cannot store a huge slug or mint the undeletable `other` rows of [D-30].
- **One column, one bound.** `field-contract.json` holds every client-writable cap, route-written collections included (`lists.name`, `accounts.nickname`, `credentials.friendly_name`), and the client's inputs take `maxlength` from it. Invite preview and join refuse a raw token over 64 characters before hashing it, as *invalid*, like an unknown one, so the bound is no oracle.

*Rejected:* per-member names, even with a shared default; a rename route (update rule plus guard is the `accounts.nickname` shape); realtime on `lists` (renames are rare); validating list ids instead of minting (would bless the hyphenated `crypto.randomUUID()` PocketBase refuses); server-minting item ids (breaks offline creation, turns retries into duplicates); dropping an unknown `slug` on import (template categories come back nameless); `slug` in the contract's `writable` map for a byte cap (push's allowlist reads that map). ([§6.4], [§6.5], [§6.7], [§7], [§7.2]–[§7.6], [§8.3], [§8.5], [§11], [D-28], [D-30], [D-31], [D-42], [D-72])

<a id="D-09"></a>**[D-09] List creation/joining is online-only.** The create/join routes are transactional server endpoints *outside* the offline outbox. Accepted v1 constraint: lists are set up with connectivity; *shopping* is fully offline. ([§7.5], [§9.3])

<a id="D-31"></a>**[D-31] Invites: one link per list, minted and rotated by the server, revoked on any departure.** As with WhatsApp's and Signal's group links, „Teilen & Mitglieder" shows the roster ([§7.4]) above **one active invite link** („Kopieren", „Teilen", „QR", expiry) and „Link zurücksetzen", which replaces it. Its device-only token was replaced by [D-294]: the server keeps a live link's token for every member.

**Only the server writes invites:** `POST /api/lists/{listId}/invite` and `.../invite/revoke`, both member-gated; `invites` has no create or update rule. The token is 32 `crypto/rand` bytes, stored as its sha256, so no member can store the hash of a chosen word. `created_by` comes from the auth token, and any departure revokes every live link on the list (`WHERE list = ? AND revoked = 0`): the leaver knows the secret, and a predicate without client input cannot regress. A partial unique index (`ON invites (list) WHERE revoked = 0`) and a one-transaction rotation hold one link per list. Revoked rows stay for the audit trail until [§13]'s sweep.

*Rejected:* several concurrent links ("which one did I give Grandma?"); client minting with `created_by` pinned in a hook (fixes one fault of three: the client still picks the token, and nothing holds one link per list); one row rotated in place (loses the audit trail); rotating only when a member is removed (leaving is the only exit). ([§7.1], [§7.3], [§7.4], [§7.6], [§11], [§13], [D-148])

### Sync engine

<a id="D-10"></a>**[D-10] A custom sync engine; do not adopt RxDB.** A shopping list is close to the best case for sync (tiny records, rare conflicts); a bespoke, heavily unit-tested outbox is smaller and more legible than a framework. ([§8])

<a id="D-11"></a>**[D-11] Conflict policy: first-committed-wins per field, surfaced but not re-applied.** When two edits change the same field concurrently, the value already committed on the server wins. The losing side gets a **passive, non-blocking toast** ("Anna had already set milk to 5"). Edits to different fields merge cleanly. Server wall-clock never decides; client clocks are never trusted. The server reports `partial` / `deleted_conflict` with `theirs_by` for the toast text.
- *Rejected: last-write-wins on arrival.* An edit queued offline for two days must not silently overwrite what the household has been acting on. Creates never conflict (fresh UUIDs) and concurrent check-offs reach the same value, so at most one field on one record can be lost.
- *Rejected: blocking modal.* The other person isn't there to negotiate, and a modal over a milk quantity in the shop is wrong.
- *Rejected: interactive re-apply* ("use my value", "restore & apply"). Conflicts and edit-vs-delete show only as passive toasts. ([§8.1], [§8.4])

<a id="D-12"></a>**[D-12] Tombstone deletes; never hard-delete syncable records from the client.** An offline device would resurrect them on its next push. Hard deletion happens only via the last-one-out cascade and tombstone GC. ([§8.2], [§13])

<a id="D-13"></a>**[D-13] Single sync loop via Web-Locks leader election.** An installed PWA window and a browser tab share one IndexedDB; exactly one leader drains the shared outbox; others stay reactive via `liveQuery`. ([§8.7])

<a id="D-26"></a>**[D-26] `checked_at` is server-stamped, outside the op vocabulary.** Clients never send it; the push route sets it when an applied op flips `checked` true and nulls it on false; the UI keeps a local optimistic stamp until the pull. As a client-stamped op field it would fire false conflict toasts on the app's most common concurrent action: two people checking off the same item converge on `checked` but virtually never on their local clocks, yielding `partial` and a toast with no real conflict. Server-stamping removes the field from the conflict surface and is more consistent with "client clocks are never trusted". **Accepted:** for offline-queued check-offs the timestamp records sync arrival, not the aisle moment, which is harmless for 7-day bucketing. *Rejected: keep the client stamp but exempt it from conflict reporting.* Keeps aisle-accurate times but *adds* a merge exemption rule instead of removing a field. ([§6.6], [§6.10], [§8.3])

<a id="D-28"></a>**[D-28] Sync consistency: a stateless inbound side, and the full membership set on the authenticated digest (2026-07).**
- **No cursor, so nothing goes stale.** Nothing is stored or advanced, so no stale-device rule exists: only a list whose stateless digest diverges is repaired, by the delta, the id set and last the full snapshot ([D-40]). A joined or created list has no local digest, so its first probe hydrates it; a row swept while a device was away is missing from the next id set, which drops it. Tombstone GC (180 days) is plain retention. Kept checked items ([§6.10]) are the growth, and [D-217] caps a list at 5,000 rows; at that size a hard delete costs each device one id set, not the list.
- **SSE is an optimistic, non-authoritative hint**: co-members see a check-off at once, and the probe and snapshot correct any echoed, stale or out-of-order event.
- **The membership set is the only way to learn a list vanished.** Memberships and cascade-deleted lists are hard-deleted ([§7.2], [§7.3]), so no per-list query sees them go. Each `GET /api/sync/digest` entry carries the caller's own membership row (`membership: {id, account, list, created, updated}`) and the list's `name` ([D-08]): the entries *are* the set, one request per tick. Own rows only ([§11]); who else is on a list is the [§7.4] roster's business.
- **An empty set is authoritative because the route authenticates.** A collection-API LIST under a rejected token answers 200-and-empty, exactly like "removed from your last list", and purging on it wipes a signed-in user's lists. The digest sits behind `RequireAuth`: a rejected token is a 401, which expires the session and aborts before any purge. A valid empty set does purge: a user who loses their only membership loses the list. `assertMembershipData` checks every source's shape at any length (an SPA fallback's `index.html` read as zero records): a malformed or missing `membership` aborts like a network failure, nothing is purged, and cached lists stay readable.
- **Order.** The digest is fetched after the drain and *before* the purge, so a transient failure aborts the whole cycle, which retries. A membership missing from the set purges its list and announces it ([D-138]); names land on `lists` rows; local digests are computed after the purge. The response only gains fields, so a cached older SPA still reads it.

*Rejected:* a cursor pull (stored state that can go stale); SSE as a pure "poke that triggers a re-snapshot" (adds a round trip to live collaboration); a separate memberships read that refreshes auth and repeats before purging (two requests per tick for an ambiguity the 401 removes); off-the-shelf engines, Replicache, ElectricSQL and PowerSync among them (the maintained ones need Postgres or a backend swap, and none ships [D-11]'s policy). ([§7.2], [§7.3], [§7.4], [§8.5], [§8.6], [§11], [§13], [D-08], [D-10], [D-11], [D-40], [D-28], [D-138], [D-173], [D-217])

<a id="D-29"></a>**[D-29] Duplicate-name creates merge; first-committed wins, discarded values toast.** An `items` create does not insert when its normalized name matches an existing **non-tombstoned** item on the list, **regardless of checked state**; the route answers `merged` with the surviving row's id, and the client drops its optimistic row and remaps queued ops to the winner. The existing row keeps its fields, **but a blank is not a value:** a blank `quantity`, `note` or `barcode` takes the create's, with no conflict (a filled barcode brings its photo, [D-266]); a restore merging into a living twin does the same ([D-176]). **Discarded values are not silent:** a non-empty field on the losing create that differs from the survivor goes through the ordinary `conflicts` reporting and raises the [§8.4] toast; a merge that discards nothing stays invisible.

**A checked match is re-activated:** the server sets `checked` = false and clears `checked_at`, while `last_bought_at` stays ([§6.6]), so typing or scanning an already-checked item, the common path, does not pile up duplicate rows. A tombstone carrying `last_bought_at` is history ([D-18]) and merges too, lifting its tombstone; one never bought stays excluded. **Accepted:** a second member's re-add during the same trip absorbs the first member's "got it"; offline concurrent adds end up as one canonical row. Its 'last bought' badge was replaced by [D-18]: the date shows on the previous-items row and on the add bar's per-list picks.

*Rejected: excluding checked rows from the match* (duplicates pile up on the common path). *Rejected: silent merges* (a lost edit must never be silent). *Rejected: letting duplicates land for users to clean up* (two members adding "Milch" offline is common, and cleanup punishes the offline use the app is built for). ([§6.6], [§6.10], [§8.2], [§8.3], [§9.1], [D-18], [D-176], [D-266])

<a id="D-40"></a>**[D-40] The sync engine's apply layer: a shadow store, a two-layer op settled by the push response, a digest that repairs what it missed (2026-07).** Server truth and optimistic value are kept apart, because a row that is both makes every path reconstruct which fields are the server's.
- **Two copies, one rule.** The shadow (`server_items`, `server_list_categories`) holds exactly the last server state, written by every inbound path and push result, never by a local edit. The view is always `materialize(shadow, op)`: shadow, then in-flight layer, then pending; a queued update without a shadow shows no row, and its push answers `row_missing` ([D-103]). Every event recomputes its rows in one Dexie transaction over view, shadow and `pending_ops`, so op and row never disagree ([D-40]). Inbound never writes an op.
- **Two layers per op.** `changed`/`base` are the pending layer, `base` being the server value the person saw at a field's first edit; `inflight` is the payload on the wire, frozen when sent. Optimistic stamps show only while their field is in a layer ([D-26], [D-45]). The drain re-sends an in-flight layer unchanged, else promotes pending, so a lost answer re-sends exactly what the server may have committed ([D-42]). An op is kept on network failure or an omitted result.
- **The push response is authoritative.** Every settling result carries the server's `record`, which becomes the shadow. A pending field whose in-flight value the server took, or with no base yet, is re-based onto it; one whose in-flight value was refused keeps that layer's base, so a re-edit built on a lost value loses too rather than replacing a winner it never saw. On `merged`, one transaction moves the shadow and the queued ops to the survivor's `record_id`. `conflicts` is toast copy ([D-11], [D-29]).
- **A denial drops the refused layer**, terminally: the pending layer stays queued, and a denied create takes its op and its row. A refused write never moves `updated`, so only the client can undo it. Every denial carries a `reason` (+ `field`) that picks the [§8.4] copy ([D-138]); an unknown code falls back to the generic line.
- **One write contract.** `backend/internal/fieldcontract/field-contract.json` holds the writable allowlist, byte caps, server-stamped fields, push limit and reason codes; Go embeds it, TypeScript imports it, inputs take `maxlength` from it. `maxlength` counts UTF-16 units and the cap UTF-8 bytes, so the input is a UX guard and `denied` the backstop, on purpose.
- **The digest finds what SSE missed.** A mutation triggers only a debounced drain, never a pull. `GET /api/sync/digest` hashes each list's sorted `{id}:{updated}` pairs, tombstones included, and the client hashes its shadow the same way (`seed/digest-vectors.json`); only diverged or never-digested lists are pulled. It is sound only because every server write bumps `updated` or changes the row set: a raw SQL UPDATE that forgets `updated` never heals. A shadow of unknown server state gets `updated` blanked, so the next cycle repairs it.
- **Delta, id set, snapshot: cheapest first,** each re-digesting and stopping on a match: rows newer than the shadow's newest (`?since=`, [D-173]), upserted; then the list's ids (`?ids`), since a hard delete changes the hash but not `max_updated`; then the full snapshot, the repair authority, for what neither explains. A queued create keeps its row throughout.

*Rejected:* one row as both server truth and optimistic value; `base` read at send time (a co-member's value arriving offline is overwritten silently, turning [D-11] into last-writer-wins); the digest as a server-change gate (every co-member edit would pull); the full snapshot after any hard delete (the nightly tombstone GC touches most lists); a bounded server change log (the cursor family again, plus a retention sweep); validating in the outbox (no UI there, and it duplicates the server's judgement). ([§8.1]–[§8.6], [§12.2], [D-11], [D-26], [D-29], [D-30], [D-28], [D-42], [D-45], [D-103], [D-40], [D-138], [D-173], [D-217])

<a id="D-42"></a>**[D-42] A re-delivered op is answered from its first delivery, never decided again.** A create whose `record_id` already exists returns **`noop`** with the current record ([D-40]); a merged one replays from `merge_log` ([D-108]), since re-running the merge with an empty base would report every co-member edit since as a conflict. An **update** is decided once per delivery: every verdict except a denial or a merge adds a hash of `op_id`, `changed` and `base` to the row's hidden `deliveries` (the newest 8), and a delivery found there applies nothing: `noop` with the current row, or `partial` naming each field that differs now. Otherwise a retry after a co-member set the field back to the op's `base` would apply again and silently undo the later edit, and a re-delivered `deleted` would re-remove a restore. The payload is in the key because edits made while an op was in flight go out under the same `op_id`. Written with a raw UPDATE, so neither `updated` nor the realtime feed moves; bounded per row, so the item cap bounds it per list ([D-217]). *Rejected:* a verdict log beside `merge_log` (one row per update, bounded only by time); a check against the shadow before resending (a retry usually precedes the next pull); a per-row "last op" (the later edit replaces it). ([§8.2], [§8.3], [D-40], [D-108], [D-217])

<a id="D-45"></a>**[D-45] `deleted_at` is server-stamped; `deleted` is an op signal, not a timestamp.** The op carries a `deleted: true/false` signal. The push route stamps `deleted_at`: `now()` on a delete, null on a restore. This mirrors `checked`/`checked_at` ([D-26]) and keeps client clocks out of the tombstone and the 180-day GC; `deleted_at` is outside the op vocabulary, annotated in [§6.6] like `checked_at`. ([§6.6], [§8.2], [§8.3])

<a id="D-308"></a>**[D-308] Screens read a list by where its rows sit, not the whole list (2026-10).** A list's rows only grow, history and tombstones included ([D-28], capped by [D-217]), and Dexie re-reads and clones a subscriber's whole result on every commit, so a screen subscribed to all of them costs more the older the list. **Each items view row carries two local fields**, set by the one view writer (`shelve` in `materialize.ts`) and never synced: `shelf` (`open` living and unchecked, `done` checked, `kept` removed but bought; none on a removed row never bought) and `shelf_at` (a checked row's check-off in ms). One index, `[list+shelf+shelf_at]`, serves every read: a home card counts in it without reading a row; the list and shop views read the open rows, the counts, and the latest run of check-offs back to the pause that ends the trip ([§6.10]); the add box, the import, the history and the rename check read living and remembered rows, the scanner only when a scan resolves. "Previous items" is the history less the trip's rows, so a row is in exactly one of the two. *Rejected:* memoising the sorting over the whole list (the reads and clones stay); Dexie's `cache: 'immutable'` (frozen rows, and the read stays whole). ([§6.10], [§8.2], [§9.1], [§9.3], [D-18], [D-28], [D-205], [D-217])

<a id="D-335"></a>**[D-335] The app needs a secure context, and says so instead of failing (2026-10).** Passkeys, the service worker, the camera, `crypto.subtle`, `crypto.randomUUID` and Web Locks exist only on HTTPS or `localhost`; over `http://` at an IP or a host name the sync threw on every cycle while the screen looked fine. So the server refuses to start while its address (`SHOPPINGLIST_RP_ORIGIN`, or `SHOPPINGLIST_APP_URL` with passkeys off) is plain `http://` anywhere but `localhost`, `*.localhost` or a loopback address (`webauthn.SecureOrigin`), naming the setting. The demo build is exempt ([D-234]): its README command binds to `localhost` ([D-235]) and it may be opened elsewhere. And the root layout reads `window.isSecureContext`: false, it shows one screen in place of the app, saying to open the HTTPS address or `http://localhost:<port>` on the machine it runs on, and starts nothing but the language. That covers what the server cannot see, a visitor at a plain-HTTP address behind its back. A sync that fails anyway says so ([D-296]). *Rejected:* libraries in place of the browser's functions (`@noble/hashes`, `uuid`): two dependencies and JavaScript hashing on every instance, where HTTPS makes them useless, for a demo that would still lack the camera, the offline start and a second tab, as Web Locks has no maintained polyfill. The libraries only where the browser call is missing (a second path nothing tests). A hand-built tab election over `BroadcastChannel`. ([§8.5], [§8.7], [D-13], [D-234], [D-235], [D-296])

### Categories

<a id="D-14"></a>**[D-14] Per-list categories via copy-on-create (name / emoji / order customizable), with an explicit "Others".** At list creation the global seed templates are **copied** into the list's `list_categories`, one row each. Renaming, changing the emoji, reordering, hiding and adding are then **ordinary row edits through the normal sync path**. A row that was never renamed keeps a `slug` link to its seed template, so its name shows in the viewer's language (de/en) and can be reset to the default. Items point at a `list_categories.id`; a null or unknown key falls back to the list's **Others** category (📦, sorts last). Assigning an item to a category (`items.category_key`) is a separate, ordinary item-field edit.
- *Rejected: overrides-first resolution.* One global read-only template list plus sparse per-list diff rows, merged on every render. It needed hand-built override IDs and used a tombstone to mean "hide", to save a few rows per list, and it pushed seed edits to every list, reordering a household's customized aisles whenever the global seed changed.
- *Rejected: one global category set (no per-list customization).* Loses a per-list aisle order for someone who shops at two different stores. ([§6.6], [§6.7], [§6.12], [§7.5])

<a id="D-15"></a>**[D-15] Global reference data is app-seeded and read-only to clients.** `category_templates` and `item_dictionary` are populated by an idempotent embedded boot seeder, never by client writes. This keeps "no client-writable global taxonomy" closed while letting clients *read* templates for name localization and offline typeahead. ([§6.7], [§6.9], [§6.12], [§10])

<a id="D-30"></a>**[D-30] The Others category is permanent.** Every list's `other` row is the fallback bucket for null/unknown `category_key`, and tombstoning it would orphan the fallback itself. The push route denies tombstone ops on `slug == "other"` rows and the UI offers no hide action for it; rename, re-emoji, and reorder remain allowed. ([§6.7], [§8.3])

<a id="D-37"></a>**[D-37] Category colours: a curated palette, copied per list, shown on headers and badges.** Every category carries a `color`: a token from a curated palette (e.g. `green`, `amber`), a plain string field on `category_templates` and `list_categories`, copied at list creation and editable per list like `icon`. The seed's templates are tested against the palette; a list row's `color` is only length-capped by the push route, and an unknown token renders gray. The frontend maps tokens to CSS values that work in light and dark themes. Colours show on category headers in both views and on the per-row category chip in the A→Z list view, which is that row's only category cue ([§9.1]). Shop tiles and category-grouped list rows carry no per-item category emoji, because the header already shows it. *Rejected: free hex colours.* Invites unreadable combinations and needs contrast handling per value in both themes; a palette is contrast-checked once, like the curated emoji. *Rejected: full-tile tinting.* Hurts readability in the shop. ([§6.7], [§6.12], [§9.1])

### Item entry & history

<a id="D-16"></a>**[D-16] Item entry: typeahead over a global localized dictionary + derived per-list picks, with auto-categorisation.** Selecting a known item pre-fills its aisle from `default_category` (overridable); a novel name is added as-typed and becomes a future suggestion for that list. **Rejected:** fuzzy/NLP matching beyond prefix + synonyms (out of scope). ([§6.9], [§9])

<a id="D-48"></a>**[D-48] Novel names are auto-categorised by head-noun (longest-suffix) matching, client-side.** On create, a null category is guessed, for a typed novel name and for a known name submitted without selecting the suggestion: the name's **longest common suffix** is scored against names whose aisle is known, and the best match that covers a whole known name wins. This amends [D-16], under which only *selected* dictionary hits got a category.
- **Suffix, because German and English grocery compounds are head-final:** Vollmilch·*schokolade* → sweets, chocolate *milk* → dairy. A prefix matcher cannot see that, and a substring match surfaces the wrong half.
- **Corpus:** the seeded `item_dictionary` mirror plus this list's own categorised items, which rank first, because only they can speak for a list's custom categories. **Client-side only**, over the Dexie mirror: it works offline, adds no route, schema or request, and the guess shows in the optimistic render at once.
- **Guardrails.** Inside a compound the matched head is ≥4 chars and more than a third of the query; starting a word, ≥3 chars („Bio Tee“ finds tea, „eis“ cannot file „Reis“). Spaces are ignored („WC Reiniger“ is „WC-Reiniger“), and a match still ends in the last word. A fixed list of inflection endings (German `-n/-en/-e/-s/-es/-er`, English `-s/-es`) is stripped from the query, and the plural ones are added to a last word of three letters or more, matching only a whole word. With no match, the last word is dropped and the rest retried down to the first, so „Milch 1,5 %" finds its head, at the price of a wrong guess such as „Kaffee Filter" → coffee. No match means Others. Tuning is pinned by `frontend/src/lib/classify-vectors.json` against the real seed. The guess is silent and can be changed on the row's category chip ([§9.1]).
- **Exceptions to the head**, for names written like a shelf label. A fruit, vegetable or herb last, after a product from another aisle, is its flavour („Chips Paprika“; „Salat Gurke“ stays produce). TK, Tiefkühl or frozen files the name under `frozen` when the list shows it, unless a known name covers the whole text. Words before mit, ohne, für, in, aus, von, with, without or for decide when they name anything („Müsli ohne Zucker“). A last word matched only by an added plural tail yields to the product before it („Avocado reif“). These key on the seed slug, so custom aisles never trigger them.
- **Languages.** Each language's rules (endings, detail words, frozen markers) are its own `Grammar`; German and English both apply under either app language, since a household types in both, and the names matched are pooled. Every rule assumes the head comes last: a head-first language needs a matcher that reads from the front.

*Accepted:* a split compound like „Salz Kartoffeln“ is misread. *Rejected:* reading the word order (German writes „Kartoffel Chips“ and „Chips Paprika“ alike); edit distance, n-grams, phonetic matching, stemming beyond the endings list, and anything that needs a model or a server round-trip ([D-16]). The matching folds umlauts/ß and punctuation, so it is a separate helper on top of `normalizeName` and leaves [D-44] untouched: nothing it produces reaches dedup, suppression or the outbox ([§8.3] [D-29]). It is also the fallback when the barcode path's Open Food Facts tag mapping misses ([§9.2]). ([§6.9], [§9], [§9.1], [§9.2], [D-16], [D-29], [D-44])

<a id="D-17"></a>**[D-17] Suggestion suppression: account-bound, global, auto-cleared on explicit re-add.** "Nicht mehr vorschlagen" writes the normalized name to a plain list on the user's **account**, **not** through the sync engine. It is an own-row PocketBase write, like editing a nickname, mirrored in Dexie so it takes effect at once, even offline. It applies everywhere, follows the user's devices, survives eviction, and is last-write-wins on one small blob, which is fine for a low-stakes preference. Explicitly re-adding a suppressed name removes it from the list, because "I do want this" outweighs an earlier "hide it".
- *Rejected: a per-list, shared, syncable `hidden_suggestions` collection.* Its own collection, API rules, deterministic IDs, un-suppression by tombstone, a sync op type and tests, all for a minor nicety.
- *Rejected: device-local (Dexie `meta` only).* On a PWA that is per install, lost on eviction, and does not follow the user to other devices. ([§6.11], [§9])

<a id="D-18"></a>**[D-18] Item history: no purchase log, the done pile is the current trip, and the last-bought date shows where it is asked for (2026-08).** History serves one purpose, re-buying: "what did we buy before?"

**History is the `items` rows themselves.** There is no `purchases` collection: a checked-off item stays in `items`, and the views bucket it client-side. The server stamps `checked_at` and `last_bought_at` together on a check-off with one `now()` ([D-26]); unchecking nulls `checked_at` and keeps `last_bought_at`, a last-write-wins stamp, not a log. Neither takes part in conflict checks.

**One predicate says what is history** (`countsAsHistory`): a living row iff it is checked, a removed row iff it was ever bought. `deleted_at` means only "not on the active list", so removing an article does not erase its purchase. The client dedup and the [§8.3] merge ([D-29]) both match remembered tombstones too, or an offline create duplicates what an online one merges, and both rank living rows first, so an older tombstone never beats a younger living row. [§13]'s tombstone GC skips rows with a `last_bought_at` ([D-100]). The remove toast says which happened („… bleibt unter „Frühere Artikel“").

**The done pile is the current trip:** the list's run of check-offs with no pause of three hours or more between two of them, while the newest is under three hours old. It is judged over the whole list on server stamps, so two people shopping together make one trip and every device agrees; a shop across midnight stays one trip, and two shops in a day are two. Three hours is a constant, not a setting: longer than any aisle takes, shorter than the gap between two shops in a day. The restore's undo ([D-200]) captures trip membership the same way. Living rows checked before the trip are „Frühere Artikel"; a removed row ignores the trip. The pile is drawn once, in the shop view's „Erledigt" section, where a tap restores; the list view plans the next trip and has no check-off control ([§9.1]).

**The last-bought date shows where the buying decision happens, whenever there is a stamp**: on the previous-items row and on the add bar's per-list picks, never on a dictionary hit, the planning row or the shop tile ([D-83]). An unprompted badge has to guess whether the user wants to know. On a suggestion the date follows the aisle (`Molkerei · gestern`) and the line wraps rather than truncating. Dates count calendar days („heute", „gestern"), and past a fortnight climb to weeks, months and years.

*Rejected:* an append-only `purchases` collection (an immutable-collection special case in the sync engine for one feature); a wall-clock split at 03:00 (cuts a shop across that hour in two), or one postponed while someone shops (a second rule on top); the done pile in the list view too; re-checking a removed row instead of tombstoning it (records it as bought today); a "forget this item" action (a server action, [D-79]); the date on the planning row (it annotates an item already chosen), in the dedup toast (after the add, too late) or in place of the aisle. **Accepted:** backup and clone drop tombstoned rows ([D-72]), and the learned-aisle classifier skips them. ([§6.6], [§6.10], [§8.3], [§9.1], [§13], [D-26], [D-29], [D-72], [D-79], [D-83], [D-100], [D-200])

<a id="D-19"></a>**[D-19] No per-item manual reordering.** Item order is shared, high-cardinality, synced state, and a sync nightmare. Ordering is by category then name. **(Contrast:** per-list *category* order and per-device *list* order are fine, being low-cardinality and/or device-local. [§9], [§9.3])

<a id="D-20"></a>**[D-20] Free-text `quantity`, not numeric.** People write "2", "500g", "a bunch"; a numeric field would fight real usage. The editor is one plain text field, with no −/+ stepper and no unit parsing. ([§6.6], [§9.1])

<a id="D-44"></a>**[D-44] Name normalization is specified once, and a shared fixture enforces Go/TS agreement.** [§9] specifies it: **trim → NFKC → lowercase → collapse internal whitespace runs to one space**, in that order (NFKC and lowercasing do not commute). NFKC composes NFC/NFD and folds ﬁ→fi and fullwidth→ASCII. It runs in Go (server merge, CLI) and in TS (client dedup and typeahead); an NFC/NFD mismatch between them lets the server merge "Müsli" where the client does not. **Deliberately excluded: no de-umlauting** (ä→ae) **and no ß→ss**, so "Müsli"/"Muesli" and "Bußgeld"/"Bussgeld" stay distinct. This function decides server-side merges, and a false positive silently collapses rows the user meant to keep, which is worse than a visible duplicate they can delete. The fixture `seed/normalization-vectors.json` (`[{in, out, note}]`) is read by both the Vitest and Go suites. The boot seeder derives ids from a normalized name too ([§6.12]). ([§9], [§6.12], [§6.13], [§8.3])

### Barcode, i18n, sync visibility, seeding

<a id="D-21"></a>**[D-21] Barcode scan: decoded on the device, looked up through an authenticated proxy, photos served from our own origin, named in each member's language (2026-07).** A scan adds a product with its picture as an ordinary `items` row riding normal sync. It is the only feature that makes the server talk to a third party, and `SHOPPINGLIST_SCANNER=off` removes it ([D-218]).

- **Decoding is local.** The `barcode-detector` ponyfill decodes with `zxing-wasm` on every browser, never a native `BarcodeDetector`, loaded at the first scan from the app's own origin. `zxing-wasm` is pinned to the exact version `barcode-detector` depends on, whose glue the ponyfill inlines, and one Renovate group upgrades both. The `.wasm` is cached once fetched, not precached ([D-95]).
- **The lookup is an authenticated proxy with a shared cache.** The browser sends a barcode only to `GET /api/barcode/{ean}?lang=` on its own origin (`connect-src 'self'`). The route requires auth, accepts only 8 to 14 digits, is rate-limited per IP, and reads the persistent `barcode_cache` (hits 30 days, misses 5 minutes) before going upstream, so the databases see only the server's IP, once per barcode per cache lifetime. The device keeps its own cache, wiped at sign-out ([D-109]). The upstream client honours `HTTPS_PROXY` ([D-210]) and names itself `shoppinglist/<version> (+<source URL>)`, as Open Food Facts asks, with `SHOPPINGLIST_SOURCE_URL`'s URL.
- **A failed upstream is not a missing product.** Only an upstream that answered "unknown", or a product without a name, is a cached miss; a transport error, an error status or an undecodable body caches nothing, or a short outage would negative-cache a live product. The user sees the same „Produkt nicht gefunden“ for both, which is why a boot probe reports a deployment that can never reach the databases ([D-260]).
- **OFF first, then the one sister it names.** For a barcode another Open … Facts site holds, OFF's v3 API answers 404 with the product type, which only selects a key in our own `siblingSites` map, so no lookup URL comes from a response. Beauty products and pet food get fixed aisles, since their tags misfile under the mapping. *Accepted:* an OFF outage covers every type.
- **Photos are stored by the server and served from our origin** (`/api/barcode/photo/{token}`, `img-src 'self' data:`). A CDN URL in an `<img>` would announce every member's IP to the CDN along with the product on the list. The photo URL comes only from upstream JSON, never a client; it must be `https` on a host in `photoHosts`, redirects are refused, and the body must sniff as JPEG, PNG or WebP under a size cap. A photo failing any check leaves the product found, shown with its category emoji. **The photo is downloaded apart from the lookup:** the lookup waits 3 seconds for it, then answers without it while the download goes on for up to 60 (one per barcode, four at once). A failure that can pass (no connection, a timeout, a 5xx, 408 or 429) keeps the row a photo-less hit, looked up again after a miss's 5 minutes and retried by a [§13] job every 15 minutes for two days; one that cannot (any other 4xx, a redirect, a body that is no image or too big, a host off the list) clears the stored upstream URL, so nothing asks for it again until the product's 30-day refresh. A photo that arrives goes to every item with that barcode and none ([D-266]). *Rejected:* a photo-less hit cached the full 30 days (a slow moment cost the picture for a month); waiting in the lookup for longer (the client gives up after 12 s); retrying every failure (a 404 asked for every 15 minutes, and on every lookup). Same origin is also what makes offline photos work: the service worker serves them cache-first from a `photos` cache that deploys keep and `logout()` empties, where a cross-origin photo would fall under the worker's `connect-src` and arrive opaque.
- **The photo route is unauthenticated and guarded by a 128-bit random token**, because an `<img>` sends no `Authorization` header ([§5.6]). The token is neither the record id (it rotates with the bytes) nor the barcode (which would make "has this household scanned X?" enumerable). The file field stays `Protected`, or PocketBase's `/api/files/…` would serve every photo past the token and the rate limit; the file is named after the token, since PocketBase echoes the filename.
- **A URL once issued keeps working**, since an item's `image_url` is set at creation, or filled in once when its photo arrives later, and never swapped. A refetch with identical bytes keeps the token, so the route can send `immutable`; the token rotates only on a real change, and the old file goes only once no item holds its URL. The [§13] sweep deletes cache rows untouched for 180 days unless an item, tombstones included, holds exactly the issued URL (equality, since a suffix match would let a member pin a row forever).
- **Each member reads the name in their language.** One upstream request fetches the main, German and English names. The item carries `name_de`/`name_en`, set only by a scan, while `name` keeps the scanner's pick; a rename clears both, so a hand-set name is shared. Two text columns, not a JSON map, keep the push route's per-field comparison. Matching widens on the client only (`nameKeys`): the server's destructive merge stays on `name` ([D-29]).
- **The aisle comes from the most specific category tag.** `mapCategory` reads OFF's tags from the last back and skips the roots, which name nothing a shop shelves by (`plant-based-foods-and-beverages`); its rules go narrow before broad. No match leaves the slug empty for the client's classifier ([D-48]).

*Rejected:* `@zxing/library` (a weaker decoder); a native `BarcodeDetector` alone (Safari and Firefox lack it); the `.wasm` from the CDN (not same-origin); photo hosts in `connect-src` (fixes the worker's fetch, keeps the privacy hole); the HTTP cache instead of the worker (loses offline photos); falling back to the upstream photo URL (a third-party host in `img-src` for good); asking each sister in turn (four requests per miss against a client that gives up after 12 s); `?product_type=all` (redirects). ([§5.6], [§6.6], [§8.3], [§9.1], [§9.2], [§10], [§13], [D-29], [D-95], [D-109], [D-210], [D-218], [D-260])

<a id="D-266"></a>**[D-266] `items.image_url` is stamped by the server from the item's barcode (2026-10).** An item shows the photo the barcode lookup stored for its barcode: an items save hook sets `image_url` from `barcode` on every create and every save that changes the barcode (push, import, clone and dashboard alike), so no client, backup or source list chooses it. A photo stored after the item was made, by a download still going or a retry, is set on every item with that barcode and no photo, through the record pipeline so each member's device pulls it; an item's photo once set is never replaced. The field is `server_stamped` in the contract. A value an op still carries is dropped, not refused, since a refusal would lose an older client's whole queued create. The client shows the lookup's photo at once as the barcode's optimistic stamp ([D-26]) and takes the server's on settle. What remains: a member can set any barcode and so show that product's photo, since the server cannot verify a scan; the CSP stays as the second wall. *Rejected:* a `pattern` on a client-written value (kept outside URLs out but let a member put any stored photo on any item); refusing an op or an import that carries `image_url` (loses an older client's queued create, punishes the member who exports). ([§5], [§8.3], [§9.2], [§10], [D-21], [D-26], [D-72])

<a id="D-22"></a>**[D-22] Localization: compile-time i18n (Paraglide), de/en at launch, additive.** The *entire* UI is localized, plus app-seeded vocabulary; user free text is never translated. Items reference categories by slug and store free-text names, so switching language changes only labels; item↔category mapping and history stay stable. ([§2], [§12.2])

<a id="D-23"></a>**[D-23] Sync visibility that never blocks use.** Sync state shows the un-synced `pending_ops` count and `meta.last_synced_at`, and never blocks use. Its banner was replaced by [D-102]: sync state is the app-bar chip ([§12.1]). ([§12.1], [D-102])

<a id="D-24"></a>**[D-24] The seed is hand-curated content, never a bulk import.** Curating grocery vocabulary in two languages is a content task, not a coding one, so the seed is its own deliverable; the code only embeds and loads it. `backend/seed/categories.json` and `backend/seed/items.json` are the project's own work, with Wikidata's CC0 labels and Open Food Facts' category tree as references. The curation (right aisle, natural wording, synonyms) is the quality bar. *Rejected:* importing a grocery database (product-level, share-alike). ([§6.12], [D-34])

<a id="D-25"></a>**[D-25] The app stores no email addresses and has no email login (2026-09).** No email or OTP login exists, and the only address the app could hold, the one an OIDC provider asserts ([D-76]), is read by nothing: personal data kept for nothing. The OIDC hook blanks the address before PocketBase sees it. Accounts stay `verified`, since PocketBase deletes an unverified record's `ExternalAuth` links on this path. The last-passkey guard ([D-32]) asks for an `ExternalAuth` row, never an address. The `email` column stays as a PocketBase system field, empty and unwritable from the client ([§11]); the one exception is the identity label in `oidc_identities` ([D-76]). *Rejected:* keeping the address "in case" (nothing uses it, and an email feature would need consent); stripping it from `meta.rawUser` too (the claims go only to the client that just authenticated as that subject, unstored). ([§4.2], [§4.4], [§5.9], [§6.1], [§11], [D-32], [D-76])

### Operator content-curation tooling

<a id="D-34"></a>**[D-34] The seed grows after launch through two operator tools, an additive append command and a read-only suggestion subcommand: not a bulk import, not client-writable, no new HTTP surface.** Both build on [§6.12]'s mechanics.
- **`cmd/appendseed`** edits only the checked-in seed JSON. It derives each `item_dictionary.id` as the boot seeder does, appends only rows whose id (or category `slug`) is new, so nobody has to read every item to add five, and bumps `seed_version`. Applying it is a restart: the idempotent boot seeder upserts the rows and clients re-mirror on the version bump. No new DB-write path, collection or admin-UI mutation.
- **`./shoppinglist dictionary-suggestions`** is a CLI subcommand the operator runs over SSH. It imports the app's own normalization ([§9], [D-29]) rather than re-implementing it in SQL, groups non-deleted item names with no match in `item_dictionary`, drops groups on fewer than 3 distinct lists (one-off typos) and prints per-category counts (`"kiwi" (5 lists) produce: 4, snacks_sweets: 1`). It is read-only: the operator corrects wording and aisle ([D-24]) and feeds accepted rows to the append command.
- *Rejected:* an HTTP route (an auth check and a "denied" test for one caller who already has a shell); a single winning category per name (hides near-even splits the counts show); a cron job with a stored or mailed report (a schedule, storage and a delivery channel for something run on demand); auto-applying suggestions (reopens the client-writable taxonomy [D-15] one step removed, and skips the human judgement [D-24] depends on); importing a public grocery database (product-level, with share-alike terms that would attach to the embedded seed, [D-24]). ([§6.13])

<a id="D-76"></a>**[D-76] OIDC login: an opt-in second login whose identity is the provider's `sub`, attached to an account only by an explicit link that never merges two accounts (2026-08).** Passkeys stay the default and the only self-serve signup; an operator may add an OpenID Connect provider and switch each login on or off, and the UI shows only the logins that are on. PocketBase's OAuth2 machinery owns the exchange and the token; the app owns the configuration, one provisioning hook, and the link and unlink routes.

- **The environment is authoritative.** `SHOPPINGLIST_OIDC=on|off` (unset = off) and `SHOPPINGLIST_PASSKEYS=on|off` (unset = on) ([D-208]). `oidc.Apply` writes the accounts collection's OAuth2 config at boot and switches it off while OIDC is off, dashboard-added providers included. The boot fails on an invalid value, on connection variables without the switch (silently dropping a login would lock its users out), and with neither login on. `SHOPPINGLIST_SIGNUP` gates new passkey accounts only: a first OIDC sign-in creates its account, so the provider decides who gets in ([D-241]).
- **The client flow is PocketBase's realtime popup**, opened synchronously at click time because Safari blocks `window.open` after an await ([D-155]).
- **The hook is the identity gate.** PocketBase falls back from the subject's `ExternalAuth` row to the account the request's token names, then to any account holding the asserted email. Neither proves the subject owns that account: the first attaches it to whatever session the browser holds, the second is a takeover by address. So the hook accepts a record only when this subject's `ExternalAuth` row points at it, and anything else gets a fresh account. It is server-side because a client fix holds only for clients that remember it.
- **A first sign-in pre-creates the account at system level**, in the exchange's transaction, so a failure leaves no identity-less row ([D-25]).
- **The link attaches; it never merges.** „Mit ‹name› verknüpfen" signs in at the provider, landing in account B; `POST /api/account/link` then carries A's session and B's fresh token, and holding both proves one person controls both. In one transaction: B with memberships or passkeys ⇒ 409 and nothing changes; otherwise B's login and label move to A and B is deleted. A is marked `verified` first, since PocketBase drops an unverified account's OAuth2 logins as possibly pre-hijacked. The exchange runs on a throwaway client, so the app's store never holds B's session: a sync cycle as B would revert every queued edit and purge every list.
- **Removal is the link's reverse.** `POST /api/account/unlink` refuses (409) unless passkeys are on and the account has one. It mirrors the last-passkey guard ([D-32]); each counts the other inside its own transaction, so both cannot pass. The record API cannot delete an OIDC login: PocketBase ships `_externalAuths` owner-deletable, so a hook refuses all but a superuser.
- **A re-auth lands in the account the device holds** ([§5.8]): it passes the expected id, the session reaches the app's store only when the ids match, and a mismatch raises `WrongAccountError`, deleting an account the exchange just created.

The 2px is therefore a relationship, not a rounding slip: one token, `--row-gutter`, feeds ListRow, PrevItemsLink and `--row-rule-inset`, and the header takes `--aisle-head-gutter: calc(var(--row-gutter) + var(--aisle-head-nudge))`; move the gutter and the header follows. The shop view puts the same header over a 14px tile grid, so the 18px lines up with rows only in the list view; the tokens claim nothing there.

<a id="D-128"></a>**[D-128] The list's last row paints no separator (2026-09).** [§9.1] gives the hairlines distinct jobs: an inset rule means "another row follows", a full-bleed one "a new section" (the previous-items door, [D-18]). So the last row emits no rule, in both sort modes; under it the row rule would stack with the door's section rule, two lines, one of them false. With one rule left the door takes no top margin: a margin only kept two hairlines from reading as one thick border, and alone it is a hole in the scroll. The two halves go together, because the second is only correct given the first. The category editor follows the same rule: its last visible row draws no rule over the hidden section's full-bleed one, and that section takes no margin.

<a id="D-127"></a>**[D-127] A control that deletes itself is not a control that did something (2026-09).** "Something in the DOM changed" is satisfied by a control that removes itself. So when the clicked control has disappeared, [D-124]'s walk compares a hash of the page with that control's markup subtracted (`restHash`), asking whether anything changed besides its disappearance. A radio, checkbox or switch is judged that way while it is still there, with its whole group subtracted: bits-ui keeps their state itself, so it moves on a click the app never answers. A tab is judged on what its panels hold, since bits-ui also shows and hides them, and the page around reflows with that. A menu item is judged against its menu closed with nothing picked, since a menu closes on any selection. Any other control still present is judged on the whole page: a picker whose job is to show its own new state would fail a check that excluded its subtree. The toaster and the sync chip change on their own timers, after whichever control caused it, so no hash includes them; a toast appearing counts as an effect. A tile check-off still passes, because its item reappears in the done section. The walk's traps were each found only by reverting the app fix and watching the walk stay green, so a guard is trusted once it has been watched failing. The walk catches the class; named assertions catch the cases whose shape it cannot judge. ([§9.1], [§6.10], [D-115], [D-124])

<a id="D-124"></a>**[D-124] A visible control must do something, and an architectural walk checks every one (2026-09).** The walk (`e2e/arch/dead-controls.spec.ts`) presses every visible, enabled control on every surface in isolation and fails unless something observable changes: URL, DOM, focus, a toast, a file chooser, a download, a new tab or a clipboard/share call. Already-selected pickers and disabled controls are exempt, with the reason in the spec. It presses only triggers and never descends into an open `alertdialog`, and every destructive action sits behind a ConfirmDialog whose appearance is the change; the few controls it must never press (one that ends its session at once) are named in the walk with the reason. Its fix to the shop/edit switch off the list page, the dead control that started it, was replaced by [D-323]: a sub-screen shows no switch. ([§9.1], [§6.10], [D-115])

<a id="D-123"></a>**[D-123] The home card's count is a bare number beside the name, and the card names no members (2026-10).** A card is one line: the name, then what is still open as a number in the name's type, a grey ✓ when nothing is open, nothing when the list is empty. „2 offen", „alles erledigt ✓" or „leer" is the link's description for a screen reader. The finished list gets no green: it is the list least likely to be opened, and green stays for actions and states. Who shares a list is set up once and rarely matters on the way to the shop, so it is off the card; the list header and „Teilen & Mitglieder" say it, and the join screen keeps the count, where it helps decide ([D-265]). `ListSummary` is shared with the ▾ quick-switcher, whose current list shows its green tick where the number would be. *Rejected:* „10 offen · 2 Mitglieder" on a second line (two facts to read, one of them noise most days); a grey or soft-green count pill (20px reads worse than the number, and the green pill already means "du" and synced); greying finished and empty names (an empty list may be about to be filled); the newest item names or the aisles still to visit (text to read, and rows read per card, [D-308]). ([§9.3], [§7.4])

<a id="D-121"></a>**[D-121] Previous items have their own display order (2026-09).** The previous-items route reuses the app-bar sort menu, with **last purchased** beside A–Z and category. Last purchased is the default and keeps [D-18]'s visible date; A–Z uses the locale collator, and category the same aisle order, fallback and headers as the active views. The choice is kept apart, as device-local `meta.history_sort`: browsing the archive must not rearrange the shopping and planning views governed by `list_row_sort`. The row is its own component, `PreviousItem`, which keeps the one-tap re-add in one unit while filtering and grouping stay in the screen. ([§6.10], [§9.1])

<a id="D-263"></a>**[D-263] The compose file hands `.env` to the app whole (`env_file`) (2026-10).** `env_file: .env` hands every line over and a missing one is absent; the server reads empty and absent alike (no `LookupEnv`). A setting exported in the shell or held in a tool's own stack variables does not reach the app; the operator note says so. The names only Compose reads (`SHOPPINGLIST_VERSION`, `_BIND`) reach the app too, and its check for unknown names passes them because `settings.Others` lists them ([D-336]). `env_file` stays required: an install without `.env` cannot boot anyway (the RP-ID), and Compose's "not found" says why sooner. `.env.example` is where each setting is explained; `internal/settings`' tests hold it to the server's settings, the hand-set OIDC endpoints excepted ([D-210]). The compose file is the app service and its volume, and the README carries it verbatim beside a four-line `.env`, so copying the two runs an instance; those tests fail a copy that differs. *Rejected: passing each setting as `NAME: ${NAME:-}`.* Every setting is written twice, an addition means editing both files, and an unset one reads as configured. *Rejected: a second, minimal compose file.* The main one is minimal, and its only difference, a bind mount, is a documented two-line change. *Rejected: `required: false` on the env file.* A silent fallback to an app that then refuses to boot. ([§14], [D-210], [D-222], [D-264])

<a id="D-264"></a>**[D-264] The egress proxy is a documented recipe, not part of the shipped setup (2026-10).** Few installs use it, so it is a `docker-compose.override.yml` in the deployment reference's hardening notes, which Compose merges in without any setting; for an OIDC provider the operator adds its hosts to the Squid allowlist line. The shipped setup has no setting, profile, entrypoint or healthcheck for it, and the app gives no boot warning that only an allowlisting proxy needed. The boot check retries instead of waiting ([D-260]), and a refused request still names the proxy ([D-210]). The recipe repeats the image's `max_filedescriptors 1024` (its `conf.d/rock.conf`, Launchpad #1978272). Its note that the recipe restricts nothing unless the host blocks the app's direct traffic was replaced by [D-267]: the app sits on an internal network. *Rejected: an allowlist inside the binary.* The app already calls only fixed hosts (the four databases, the photo-host allowlist, the configured provider); a check inside the process falls with it, and outlasting a compromised app is the proxy's only point. *Rejected: a shipped `docker-compose.egress-proxy.yml` with a `SHOPPINGLIST_EGRESS_PROXY_ALLOW` setting.* Still a file, a setting and an image each release keeps working, for an optional setup. *Rejected: making the app wait for a healthy proxy* (`depends_on: service_healthy`). It keeps the app down whenever Squid never becomes healthy. ([§14], [D-210], [D-260], [D-263])

<a id="D-267"></a>**[D-267] With the egress proxy, the app is on an internal network only, and the reverse proxy joins it (2026-10).** In [D-264]'s recipe the app is on a network with `internal: true` and nothing else (`networks: !override`), which has no route out and no DNS, so the proxy, on that network and `default`, is its one way out; on `default` beside the proxy, a compromised app could skip it. A container only on an internal network publishes no port (Docker 29), so the app's port goes (`ports: !reset []`) and the reverse proxy, in Docker, joins the network and reaches `shoppinglist:8090`. The network has a fixed name, `shoppinglist_internal`, so a proxy in another Compose project attaches to it as `external`. `!override` and `!reset` need Compose 2.24.4. A provider on the operator's own network goes through the proxy too, since `NO_PROXY` has no route to bypass to. *Rejected: a `socat` forwarder publishing the port for a reverse proxy on the host.* One more container, a workaround for a setup the hardening does not need to serve: a host proxy runs without the recipe. ([§14], [D-210], [D-260], [D-264])

### UI layout

<a id="D-268"></a>**[D-268] A planning row's quantity is quiet text under the name (2026-10).** Both button states, a set quantity and „+ Menge", are muted text under the name with no border and no pencil, right-aligned in the same `--qty-w` box, so opening the editor still does not reflow the row ([D-86]), and its 30px height with the `hit-target` inset keeps the 44px tap target ([D-56]). **The only sign at rest that a set quantity is a control is where it sits;** a hover (pointer devices only) or a press shows the shop tile chip's fill, keyboard focus the global outline. Discovery rests on two things: „+ Menge" says it is an action, and tapping the name opens the item sheet, which edits the quantity too, so the inline edit is a shortcut nobody needs to find. The editor keeps `text-base`: below 16px iOS zooms the page on focus. Its size was replaced by [D-275]: `text-qty`, 13.5px. **Why:** a bordered quantity at body size read bigger than the item. *Rejected:* a filled chip at rest (the shop tile's, chosen against in review); a smaller outlined box (every row keeps a box and the list reads as a table); „+ Menge" in the link green (too loud, and the plus already says "add"); a dotted underline or a faint pencil on set quantities (ink on every row for a shortcut). ([§9.1], [D-20], [D-86], [D-119], [D-213])

<a id="D-275"></a>**[D-275] An item reads in three tiers, name over quantity over note, and quantities are set in Readex (2026-10).** **The rule:** name, then quantity, then note, about 2px apart, with no quantity under 13px and no note under 12px, at the default text size most people read. Names are 16px in the planning row (`text-base`), 17px on a comfortable tile (`text-tile`), 15px on shop rows, compact and photo tiles (`text-name`). Quantities are `text-qty` (13.5px) in the planning row and the shop chip; the planning row's stays muted and under the name ([D-268]). Notes are `text-note` (12px). Other small print stays on `text-micro` ([D-213]), and the done rows, already struck out, keep their sizes. Tiles keep their height. **Quantities and counts are Readex with tabular figures**, not monospace: at the same size Readex reads larger and matches the app; `--font-num` is left to code-like text such as the invite link. *Rejected:* two steps (17px planning names, 15px chips), which cost about a row per screen in the planning list and cut long German names in the tiles. ([§9.1], [§12], [D-83], [D-184], [D-213], [D-268])

<a id="D-119"></a>**[D-119] Planning rows spend their width on the item; removal lives in its detail sheet (2026-09).** The row has no trash button; quantity stays the direct inline edit. A button would cost every compact planning row width for an occasional action the detail sheet already offers with undo. Tapping the name or category chip opens the sheet, whose header pairs a circular destructive trash action with the circular close; both keep 48px effective targets, and the trash names the item to assistive technology. The app and `/dev/gallery` share that action component. Its rejection of a swipe gesture was replaced by [D-289]: a swipe to the left removes too, as a shortcut beside the sheet. ([§9.1], [D-116], [D-117])

<a id="D-117"></a>**[D-117] The dev gallery is a live fixture preview with a permanent current/proposal comparison (2026-09).** `/dev/gallery` shows list contents from fixtures with the app's own components and styles, instead of real edge-case lists or a separate prototype; fixture callbacks stay in memory. The first row is always the exact current app; a proposal renders the same components with only its CSS delta scoped to its wrapper, so "before" is explicit and no second implementation drifts. App and gallery share `.shop-grid`, with columns and density spacing measured against the list container, not the viewport. Cases cover mixed items, text at the field limits and in mixed writing directions, photo shapes and failures, empty, completed and loading states, themes, densities, locale and enlarged root text; not auth, sync, scanning or item editors. **Still open as a proposal:** display quantities wrap, a maximum-length one capped at 38% of a shopping row, and at enlarged text a planning row's controls reflow below the name when the row has less than 19rem. Category headers paint above every per-tile control, and the list's add dropdown above both, so the info door cannot float through a sticky aisle header. ([§9.1])

<a id="D-116"></a>**[D-116] Refine the existing tiles and rows; keep shopping dense and direct (2026-09).** The user rejected the gallery proposal's remaining layout and interaction changes: its larger rows sacrifice too much of the overview. One tap on a shopping tile's main area checks off the item; names, quantities and useful notes are readable at a glance, with details available for overflow and product information. A refinement is judged at the same viewport, text size and density against the current components: visible item count, legibility and taps for ordinary tasks matter together. Direct editing controls and the density choices stay. The approved palette ([D-114]) and shared header sorting ([D-115]) stand; the rest of the prototype is a rejected exploration, not an adoption plan. ([§9.1])

<a id="D-115"></a>**[D-115] One sort menu in every app bar, whose icon is the order (2026-09).** Sorting sits in the header, where it can also be changed while shopping.

- **One component, `SortMenu`:** an app-bar icon button opening a keyboard-accessible radio menu, used by `ItemSort` (both list views, previous items) and `ListSort` (the home), so the screens cannot drift. The trigger shows the mode only through the selected option's icon, and its accessible name appends the label („Sortierung: Aktivität"). An optional `action` holds the home's „Reihenfolge ändern …" ([D-90]).
- **Item order is one device-local preference, by category by default.** Both views read `list_row_sort`, and one choice sets both. Until a choice is saved, both sort by category, the user's pick: the order the list is shopped in, where its category colours read best. Category order keeps the aisle groups; A–Z is one flat grid with the same tiles and densities. Done items stay newest-checked first. Previous items add „Zuletzt gekauft" and keep their own preference ([D-121]).
- **Every option's icon has the same arrow,** so each says "order" on its own (a bare clock read "history", a funnel "filter", a grip "drag me"). All use lucide's sort arrow at x=3–11 and differ only in the right-hand mark: `arrow-down-a-z`, `arrow-down-up` (hand-made order), and two drawn in-repo because lucide has none for "category" or "time", `ArrowDownGroups` and `ArrowDownClock` (activity and last purchased), which copy lucide's arrow paths exactly.

*Rejected:* A–Z as the editing view's default (only continuity); `layers-arrow-down` (its arrow hangs below the glyph and blurs at 19px); `arrow-down-narrow-wide` (bars mean "by size"); all-stock icons (`arrow-down-wide-narrow` for time nearly mirrors it at 19px); one icon for every mode (the trigger would not show the order); lucide's `Icon` component (not exported; the barrel could put every icon in the bundle). ([§6.10], [§9.1], [§9.3], [§14], [D-90])

<a id="D-114"></a>**[D-114] Colours: the Laub palette, neutral greys and one green split into a fill and a text colour (2026-09).** The user chose **Laub** from five OKLCH palettes: an opaque header over a pale body, a richer green for selection and hover.

- **Green lives in the primary alone.** Neutrals carry ≤ 0.012 chroma; `--background` is the body, `--surface` the opaque layer for headers. Dark is charcoal, each raised layer one lightness step up. Delete is brick (hue 30), category red crimson (hue 18), so a category never reads as an error ([D-37]); category colours share one lightness and chroma per theme and differ by hue ([D-251]). Tokens are OKLCH written as hex, which the token test reads.
- **Fill and text are two tokens,** because in dark no green does both: a light one makes pale slabs of filled controls, and a fill dark enough for a white label is too dim as text. `--primary` is the fill under white; `--primary-text` is text and lines; in light both are `#05773b`, and both meet AA. **Rule:** a solid `bg-primary`, and a border drawn with it, is a fill; text, a border or ring on the page, a `bg-primary/NN` tint, the category tint's fallback and the toast's undo pill are text. Dark `--primary-press` is darker, so the dark secondary button's text is `--primary-text`, kept at 4.5:1 on its hover by `--primary-line`.
- **The app icons take the same roles:** `--primary` for the ground and the check, `--primary-press` for the clip, `--primary-line` for the lines; `favicon.svg` is the source of every PNG and of `favicon.ico`.

*Rejected:* one primary for fill and text; sage-tinted neutrals (one wash, and the app looked generic). ([§6.7], [§12], [D-37], [D-251])

<a id="D-49"></a>**[D-49] The app shell is a fluid single column capped at `--app-max` (820px); the shop tile grid is responsive (2/3/4 columns); phones are unchanged.** The column widens to a reading cap, the single token `--app-max` in `app.css`, and the shop tile grid, the one surface that earns width, gains columns, topping out at four. Its breakpoints were replaced by [D-83]: one auto-fill rule, with the same column counts. The bottom **Sheet** tracks `--app-max`; the **toast** keeps its narrower snackbar cap, as a centred floating bar. *Rejected: a multi-pane desktop layout* (a list-nav sidebar and a main pane). Highest effort, fights the mobile idiom, and over-builds for a product whose wide-screen use is "open in a browser tab". *Rejected: container queries on `.app-shell`.* The Sheet is a `position: fixed` descendant of `.app-shell`, which could become its containing block and anchor it to the scrolling document; viewport `@media` queries resolve identically because the shell tracks the viewport up to its cap. *Rejected: fluid `clamp()` everywhere.* Scope creep that does not visibly help once the shell widens and the grid responds. ([§9.1], [§12], [D-83])

## Deferred and out of scope for v1

- Live presence / typing indicators.
- View-only members / roles [D-06].
- Manual item reordering: rejected as a sync nightmare [D-19].
- Numeric quantity: rejected in favour of free-text [D-20].
- Fuzzy/NLP typeahead matching beyond prefix + synonyms [D-16].
- Canonical cross-locale item linking for history (names are stored as display strings; fine for a shared-locale household).
- RP-ID domain-migration story (documented caveat only).
- Seeding barcodes into `item_dictionary` (scans are cached device-locally in `scanned_products`).
- Syncing a user's custom *list* order across their own devices (it is device-local; the upgrade path is a nullable `memberships.sort_order`).
