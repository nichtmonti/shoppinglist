# Changelog

What each tagged release of shoppinglist changed, newest first. `[D-nn]` points into the [decision log](docs/internals/decisions.md#decision-log), `§n` into [`design.md`](docs/internals/design.md).

Every release tag sits on the commit that adds its entry here (`docs(release): vX.Y.Z change history`). A release's entry is also the top of its Codeberg release page, above the commit list (`scripts/release-notes.sh`, run by the release pipeline), and a tag without one fails the release before anything is published.

Changes land under **Unreleased** in the commit that makes them; the release commit turns that heading into the version's.

## Unreleased

- **For operators: a server started on data a newer version has changed refuses to start**, and names the backup the newer version made before changing it. Going back to an older image without restoring that backup used to start and run the old version over a database it did not know ([D-345]).
- **An app tab left open from before an update reloads when another tab brings the update's new storage.** It kept running the old version on the device's updated storage and could save changes in the old shape ([D-344]).
- **A list's own screens keep their name in the browser tab.** When the list loaded slowly, its categories, previous items and import screens could show the list's name there instead.

## v0.17.1: nothing from a list kept past a sign-out in another tab, one-line list cards, and releases you can rebuild yourself (2026-10)

- **A list change that arrives just after you sign out in another tab is no longer kept.** It could be stored on this device for whoever signs in next ([D-109]).
- **A passkey with an RSA key shorter than 2048 bits is refused**, when it is created and at every sign-in, as NIST's minimum through 2030 asks. Passkeys from phones, password managers and security keys use elliptic-curve or 2048-bit RSA keys, so none is affected.
- **The cards under "My lists" are one line.** Each shows the list's name and, beside it, how many items are still open, a grey ✓ when everything is checked off, and nothing for an empty list. The number of members is gone from the cards; the list's header and "Share & members" still show it. In the list switcher, the list you are in has its green tick where its number would be ([D-123]).
- **A scanned product's number says what it is.** Under the photo in "Product details" and "Edit item", the long number now has "Barcode" in front of it, and the “Copy barcode” button beside it is gone.
- **[`CONTRIBUTING.md`](CONTRIBUTING.md) says how to send a change and what it must test.** A change comes as a pull request against `main` on Codeberg; a new feature brings its tests, and a bug fix a test that fails without the fix.
- **Releases can be rebuilt byte for byte.** Built again from its tag, a release's binaries and zips come out identical, so you can check a download against the source ([how](docs/deploy-reference.md#rebuilding-a-release-yourself), [D-338]).

## v0.17.0: errors that say what went wrong, and a server that stops on a setting it does not know (2026-10)

**For operators.** Before upgrading, check that every `SHOPPINGLIST_` variable in your `.env` (and `SQLITE_PRAGMAS`, if you set it) is one the [deployment reference](docs/deploy-reference.md#environment-variables) lists: the server now refuses to start while it finds another, and names it. With passkeys off (`SHOPPINGLIST_PASSKEYS=off`), check that `SHOPPINGLIST_APP_URL` is the `https://` address: a plain `http://` one anywhere but `localhost` stops the server too, as it already did with passkeys on. If you filter or alert on the server's warnings in the container log, match their new form (below).

- **The user guide says what needs a connection** (creating, joining, renaming or leaving a list, invite links, account changes, importing a backup, an unknown barcode), how to sign in through a household's own provider ("Continue with ‹name›"), and "My lists" for the app's start page; the README says where to switch the language.
- **Citations in the docs and this changelog are links**: a decision such as [D-336] opens its entry in the decision log, and a section such as [§5.7] its heading in the design document.
- **The operator docs state each fact once and link to it**, and correct three details: with `SHOPPINGLIST_ADMIN_UI=off` the dashboard's enrolment link is not printed at all, plain `http://` also works at a `*.localhost` name or any loopback address, and the release zip holds the licences and the operator docs beside the binary. The README points to [docs/operating.md](docs/operating.md#backups) for backups.
- **`CONTRIBUTING.md` says what `task --list` shows** (the tasks to run, not every task) and links to where the test layers are listed.
- **The docs quote the app and the server word for word.** The user guide names the buttons as they read ("Choose a backup file…") and says “check off” as the app does; the operator page's client-error section lists every `context=` the app reports, the OIDC sign-in failure is quoted as the server logs it, and the `dictionary-suggestions` sample is spaced as the command prints it.
- **The deployment docs cover the checks at start**: the server refuses a plain `http://` address and a setting it does not know, and warns when a proxy sends a forwarding header it was not told to trust ([docs/deploying.md](docs/deploying.md), [docs/deploy-reference.md](docs/deploy-reference.md#1-send-the-app-the-real-client-ip)).
- **The README opens with the app's logo, a one-line summary and badges** for the build, the license, the Docker image for amd64 and arm64, sign-in with passkeys or OIDC, and what it is built with (Go, PocketBase, SQLite, SvelteKit), followed by links to the demo, the deployment guide, the user guide and the changelog. The note that the app is pre-1.0 moved to “Is it for you?”.
- **The cron jobs in [docs/operating.md](docs/operating.md#cron-jobs) go by the names the log gives them** (`tombstone_gc`, `orphan_sweep` and the rest), so a `… failed` line in the log points at its row, and the table comes from the code that schedules them.
- **`.env.example` no longer suggests trying the app on your LAN without a proxy** through `SHOPPINGLIST_BIND`. Over plain `http://` at any address but `localhost` the app does not work; the line now says to publish on every interface only for a reverse proxy on another machine.
- **`shoppinglist serve --help` prints the help without any settings**; it asked for `SHOPPINGLIST_RP_ID` first.
- **Built with Go 1.27.3**, which fixes a standard-library vulnerability (GO-2026-6809).
- **A misspelt setting stops the server instead of being ignored.** `SHOPPINGLIST_SIGNUPS=closed`, say, used to start an instance with sign-up open; the log now names the variable and points to the list of settings. The same goes for a setting removed in an earlier release that is still set, and for `SQLITE_PRAGMA` written without its final S ([D-336]).
- **The server's warnings and errors in the container log are in the standard `key=value` form**, with their level: `level=WARN msg="shoppinglist: …" key=value` instead of `shoppinglist: WARNING …`. A filter or alert that matched the old wording needs the new one; the lines that say how the server is configured at start keep their form.
- **Every server error the app answers with now says what went wrong in the container log**, as `level=ERROR msg="shoppinglist: request failed" error=… route=…`, a crash inside a request included. The cause used to be only in the request log, which an instance with `SHOPPINGLIST_ADMIN_UI=off` cannot read and the demo does not keep ([D-209]).
- **A failed barcode lookup names the site and what it answered** in that line (a refused connection, `answered 429 Too Many Requests`), and a product photo from a host the server does not download from is logged with the host instead of being dropped without a word.
- **A server behind a reverse proxy that it does not know about says so once.** When requests carry `X-Forwarded-For` (or a similar header) while `SHOPPINGLIST_TRUSTED_PROXY_HEADER` is unset, every visitor has the proxy's address and shares one rate limit; the container log now warns about it once per start.
- **Signing out can no longer leave your lists on the device when deleting them fails.** If the browser's storage refuses the deletion, the app now deletes all of its data on the device and starts again, instead of showing the sign-in screen with the lists still stored for the next person to sign in ([D-55]).
- **A sync the server keeps refusing says "Sync error · reload"** instead of "Server not answering": a request refused as wrong (an app tab from before an update, a proxy that blocks it) fails the same on every try, and the server did answer ([D-296]).
- **A barcode the server could not look up no longer reads "Product not found".** When the lookup gets no answer (the product databases are busy or down), the scanner now says "The product can't be looked up right now. Type the name instead." ([D-293]).
- **A change the device cannot save is no longer lost without a word.** When the browser's storage refuses a write (it is full, say), the app now says "Your change could not be saved on this device. Reload the app and try again.", and a name typed into the add field stays there instead of vanishing ([D-293]).
- **The operator docs match the server again.** Restoring a backup from the dashboard happens on the running server (only the manual restore stops it); the photo-retry job, every 15 minutes, is listed among the jobs; the release binary comes zipped and, without Docker, reads no `.env`; a failed passkey registration points to `SHOPPINGLIST_RP_ID` as well as `SHOPPINGLIST_RP_ORIGIN`; and the labels "Connect with ‹name›" and "Install Shopping list" are quoted as the app shows them. The deployment reference no longer repeats the guide's steps (the Caddyfile, first boot, upgrades, the superuser command); it links to them and keeps what the guide leaves out.
- **"Leave list" can be confirmed once the app has checked who is still on the list.** The warning that leaving deletes the list for everyone depended on a member list that could be out of date; until the check answers, only "Cancel" works ([D-293]).
- **A list you just created or joined no longer says it isn't among your lists for up to a minute** when the connection drops right after: the app tries again within seconds.
- **Connecting your identity provider in settings no longer blames the window or the provider when the server fails afterwards.** Once the provider has accepted, a failure says what happened ("Something went wrong.", or that the connection or the session is the problem) instead of "Connecting failed. The window was closed or the provider refused."
- **An import that fails because of the connection or the session says so** ("Couldn't reach the server. Try again." or "Your session has expired. Sign in again, then try again.") instead of "Import failed".
- **Errors in the app that nothing catches are now sent to the server log too** (`client error … context=uncaught`), not only those that break a page: a change the phone could not save, say, used to fail with no trace outside the browser's console ([D-197]).
- **A sign-in the device cannot store or read reaches the server log.** A phone whose storage refuses the saved sign-in signed you out at every start, or brought a sign-out back after a reload, with no trace outside the browser ([D-197]).
- **A sign-in screen whose code fails to load shows the error page with "Reload"** instead of a blank page.
- **A passkey refused because of the server's settings says which one** in the container log: `check="SHOPPINGLIST_RP_ORIGIN must be the origin users open…"` when the address bar's origin differs, and a hint on `SHOPPINGLIST_RP_ID` when a passkey was made for another domain.
- **The server no longer starts when it cannot apply its built-in aisles and dictionary.** It logged the failure and served on, and lists made then had no aisles for good; nothing is half applied, so the next start tries again. The same holds when an invite-only instance cannot tell whether its first account exists.
- **Accounts the daily sweep deletes (on no list and unused for 60 days) are logged with their number**, so an operator can tell why an account is gone; the fallback to the OIDC endpoints of an earlier start is logged in the new form too.
- **When several settings are wrong, the server names all of them at once** instead of stopping at the first ([D-337]).
- **The settings table in the deployment reference comes from the code**, so its defaults are the ones the server applies. The four settings every command reads (`SHOPPINGLIST_APP_URL`, the two trusted-proxy ones, `SQLITE_PRAGMAS`) now close the table, and the demo's table lists only its own two settings ([D-337]).
- **A `SHOPPINGLIST_RP_ID` written as a URL is named in the error**, with what to write instead (a bare domain such as `list.example.com`); before, the log showed a passkey library's message that named neither. The other passkey setting errors point to the deployment reference.
- **The demo's start screen says it gives you three example lists**, not one.
- **The app says when it is opened at an address it cannot work on.** Over `http://` at a machine's IP or name (a phone on the home network, say), the browser withholds what the app needs, so lists stayed empty and nothing typed in reached the server, with no sign of it. Every page now says instead to open the app at its `https://` address, or at `http://localhost:<port>` on the computer it runs on ("This address isn't secure"), and the server refuses to start while its own address is plain `http://` anywhere but `localhost`, naming the setting. The demo is exempt from the refusal and shows the same page ([D-335]).
- **The sync status no longer looks fine while the sync is broken.** When syncing fails three times in a row with nothing of yours waiting, the line under the list's name says how old what you see is ("As of …") at once instead of after 5 minutes, and the cloud turns into the clock. When the app itself is at fault rather than the connection or the server, it says "Sync error · reload", and its sheet offers "Reload" ([D-296]).
- **"Try it" leaves you on the overview of the three example lists** instead of opening one of them ([D-234]).
- **With `SHOPPINGLIST_ADMIN_UI=off`, and in the demo, the server log no longer offers a superuser.** Gone are the link to the removed dashboard, PocketBase's line naming it and, in the demo, the hint to run `superuser upsert`; a line says where the server is reachable instead. An instance with the dashboard keeps its one-time setup link.
- **A passkey sign-in the server cannot start now says so** ("Sign-in could not be started."), when there were too many attempts or the server cannot be reached. It said "That didn't work. Please try again.", which pointed at the passkey.
- **An invitation link created before v0.13.5 is no longer shown on the phone that created it either.** Like everyone else on the list, press "Reset link" there for a new one. Such links expire 30 days after they were made, so few are still valid.
- **"Cancel" during a sign-in with your identity provider now also closes its window.** It stayed open behind the app.
- **The "Install Shopping list" card no longer disappears when the browser is put in full screen.** A full-screen browser tab read as the installed app.
- **PocketBase's dashboard (`/_/`) and the files it serves get PocketBase's own Content-Security-Policy again.** The app's headers had replaced the dashboard's with one that only forbade framing, and gave product photos the app's policy instead of PocketBase's sandbox.
- **The segmented choices behave as their kind does.** The list's "Shopping"/"Editing" switch and the language and theme choices in settings now choose with the arrow keys, as radio buttons do. The share sheet's "Invite link"/"QR" switch is announced as tabs over their panel.
- **Leaving a list right after rejoining it on another device now really leaves it.** The app could pick the stale membership from before, so the list came back at the next sync.
- **Signing out while the app was syncing can no longer leave the account's lists behind on the device.** The sync could write its list of memberships just after the sign-out had cleared them ([D-109]).
- **Scanning works again after a first scan that failed offline,** without reloading the app. The decoder that failed to load stayed broken, and every later scan, online too, ended in "Barcodes can't be read right now. Type the name instead." ([D-95]).
- **Adding a passkey on a device that already holds one for your account now says so** ("A passkey for this nickname is already stored on this device.") instead of quietly replacing the old one. The replaced passkey's entry stayed in "Passkeys" though it no longer worked, and counted as a way in, so the last working passkey could be removed.
- **A hardware key whose counter once went backwards is no longer reported as possibly cloned at every later sign-in.** The server log warned on each login after the first warning, even once the counter advanced normally again.

## v0.16.1: nightly backups from the first start, a ‹ that still goes back after a reload, and screens ready before you open them (2026-10)

**For operators.** Nothing to do before upgrading. From the first night, the server writes a backup to `pb_data/backups/` at 03:00 UTC and keeps the newest seven. They sit on the same disk as the data, so copy them elsewhere or send them to S3. The upgrade removes the `webauthn_sessions` collection.

- **The server backs itself up every night.** PocketBase's scheduled backups are now on from the first start: at 03:00 UTC into `pb_data/backups/`, the newest seven kept, next to the data, so copy them elsewhere too. An instance that already had a schedule keeps it; change it, send the backups to S3 or empty the schedule in `/_/` → Settings → Backups. A failed backup also shows in the container log ("backup failed") ([D-334]).
- **Passkey sign-ins in progress are held in memory instead of the database**: the `webauthn_sessions` collection is gone from the dashboard, and so is its ten-minute cleanup job. A sign-in under way while the server restarts has to be started again ([D-03]).
- **After the browser reloads a page, its ‹ still goes back** to the screen you came from instead of putting a copy of that screen on top, and a reordering mode that was open stays open. Safari often reloads tabs left in the background ([D-230]).
- **The app loads every screen's code once the first screen is shown**, from the copy it keeps on the device (so not on a first visit), and opening a screen later loads nothing. On iPhones this should make the "One moment…" reload after a failed screen load rarer ([D-202]).
- **`CONTRIBUTING.md` says what the devcontainer mounts** from your home directory (the coding agents' folders and `~/.ssh`, read-only) and how to go without them.

## v0.15.1: sync changes that apply once, one look across the app, aisle colours in the shop's list, and settings that open after a cut-off answer (2026-10)

**For operators.** Nothing to do before upgrading. The server adds a hidden column to items and categories when it starts ([D-42]).

- **For operators: an administrator's token on the app's own routes is answered "not allowed".** With `SHOPPINGLIST_ADMIN_UI=on`, a superuser's token sent to a route that wants a signed-in account was answered as if no one were signed in (401); it is now refused as the wrong kind of sign-in (403), as PocketBase's own routes do.
- **For operators: the server's warnings and failures also reach the dashboard's log.** The barcode scanner's reachability warning, the proxy-header warnings, a failed start-up step and the built-in list update were only in the container log; they are now in both, and a value that holds a space or a line break is quoted, so each event stays one line.
- **Settings no longer fails to open after a page was left mid-load.** When the app moved on while the server's answer about the sign-in methods was still arriving, the cut answer was kept as if it were empty, and "Settings" then showed the error page until the next full answer. A reply that arrives incomplete now counts as no reply ([D-76]).
- **A change that reached the server while its answer was lost no longer undoes what someone did after it.** The phone sends such a change again, and when another member had meanwhile put the item back on the list, restored it or set its quantity back, the repeat silently reversed that. The server now recognises a change it has already decided and applies it only once ([D-42]). The update adds a hidden column to items and categories, filled as changes arrive; nothing to do before upgrading.
- **A late update from the server no longer undoes your next edit.** When news of an older change reached the phone after its own change had been saved, the next edit of the same field was refused as if someone else had changed it first, with a message naming you. Such late news is now ignored.
- **An edit made while someone else's change arrived no longer replaces it unseen.** If another member renamed an item or changed its quantity while you had it open, saving your edit overwrote theirs without a word; now the first change stays and you are told, as for any other conflict ([D-11]).
- **A second change made while your first is still on its way no longer overrides another member.** When your first change lost to one another member had made first, a second change to the same field, made before the phone heard back, replaced theirs without you ever seeing it. Now it loses too, and you are told, as for the first ([D-40]).
- **A category you removed stays removed after six months.** The daily cleanup deleted a removed built-in category after 180 days, and the category editor then offered it again under "Newer lists also have these categories:" ([D-251]).
- **A revoked or replaced invite link is kept for 30 days after it was revoked.** The daily sweep counted from the day the link was made, so a link revoked on its 29th day was deleted the next day.
- **A backup file that gives two categories the same key is refused.** The server restored it, and the items of the first category landed in the second; the app's own exports never contain one ([D-72]).
- **Undoing a tick-off on a duplicated list keeps the earlier purchase date.** A list made with "Duplicate" did not carry the date a tick-off had replaced, so tapping "Undo" on a copied tick dropped the item from "Previous items" instead of restoring its earlier purchase ([D-72], [D-303]).
- **A change the server fails to save is now logged.** When a database error stopped the server from saving one of a phone's changes, the phone kept the change and sent it again, but nothing said why; a change that kept failing was retried forever without a trace. Each failure is now a warning in the server log, "sync push: op not settled", with the error ([D-191]).

## v0.7.1: simpler OIDC setup, and sign-in failures that say why (2026-10)

**Connecting an OIDC provider takes one address instead of three** ([D-208]). Set `SHOPPINGLIST_OIDC_ISSUER` to your provider's issuer (for Pocket ID, its own address), and the server reads the sign-in, token and user-info addresses from the provider's published configuration at every start. Typing those three addresses by hand was the easiest way to get the setup wrong: Pocket ID, for example, keeps two of them under `/api/oidc/`, unlike most others. If the provider is unreachable when the server starts, it uses the addresses it found last time, so a provider outage no longer keeps the app, passkey sign-ins included, from starting. The three address variables still work, for providers without a published configuration and for existing setups.

**A sign-in that fails on the server's side says so** ([D-209]). When the provider had accepted you but this server could not complete the sign-in, the app said the window had been closed or the provider had declined. Neither was true. It now says the provider accepted and the server's OIDC setup failed, and the server log names the cause and what to check: the client secret, the token or user-info address, or the callback URL. Before, the cause was visible only in the admin dashboard.

**New OIDC accounts always have a name.** An account created through a provider takes its nickname from the provider's display name, then its username, then the first part of the e-mail address; if the provider sends none of these, it is "Member" instead of an empty name in other members' list of members. It is held to the same length limit as any nickname.

**For operators.** No database change. To use the simpler setup, replace `SHOPPINGLIST_OIDC_AUTH_URL`, `_TOKEN_URL` and `_USERINFO_URL` with `SHOPPINGLIST_OIDC_ISSUER` (setting both is refused). The provider's callback URL is `<app address>/api/oauth2-redirect`; no logout callback is needed. See "OIDC login" in docs/deploy-reference.md.

## v0.6.0: a rebuilt sync engine, lists that open whole, and an app icon (2026-10)

**The sync engine works from one rule** ([D-40]). Each device now keeps two copies of every item: what the server last said, and your own changes not yet confirmed. What you see is always the one with the other on top. Before, a single copy had to be both, and nine separate mechanisms worked out after the fact which parts were whose. Three things you can notice:

- **A change made twice in a row on a bad connection is no longer lost.** If your phone's first change reached the server but the answer didn't come back, and you then changed the same thing again, the second change was dropped and you were told that *you* had already set the first value. Now your latest change stands, with no notice.
- **A change the server refuses shows the right value at once.** If someone else had changed the item in the meantime, you now see their value straight away instead of an older one until the next background check.
- **Background repairs are rarer.** Items you had just added no longer made the device's check against the server fail now and then, which started unnecessary full downloads of the list.

**Opening a list no longer flashes** ([D-205]). A list used to appear in steps: the app's name with an empty list for a moment, then the items. Lists, the home screen and the settings now appear complete in their first frame, from what the device already holds.

**The app has its icon back in the browser tab and on the iPhone home screen**. The icon existed, but only after the app had loaded, so bookmarks, the tab and "Add to Home Screen" often showed none.

**For operators.** No server change of any kind. Each device converts its stored data to the new format on the first start after the update, keeping any changes still waiting to be sent; there is nothing to do.

## v0.5.0: sign-out leaves nothing behind, the catalogue learns the Asian market, and the typeahead ranks what you buy first (2026-09)

A review of the seed vocabulary, a round of typeahead fixes, and an audit that turned comment-only rules into tests. Those tests found two sign-out leaks and three colours that had never rendered as written.

**Signing out no longer leaves the previous account behind** ([D-145], [D-148]). After a sign-out, the next account's home screen briefly rendered the previous account's list names: five live stores (lists, the list index, hidden suggestions, the custom list order, the last-sync time) kept their cached value across the wipe and replayed it to the next reader until the local database answered. The wipe now invalidates every store's cache, so they start empty; within one account nothing changes. Separately, the share sheet's cache of invite links you minted, the only plaintext copy of a token that lets anyone join the list, survived sign-out entirely. It is now wiped with the rest of the account's data. On a device used by one person neither leak exposed anything; on a shared one, both did.

**Signing in shows your lists loading, not an empty account** ([D-182], [D-185]). Right after signing in, the home screen showed the welcome for a brand-new account, "New list" included, until the first sync answered: long enough that people created lists they already had. It now says "Loading your lists…" until the lists arrive. Offline it says they come once you are connected, and after a few seconds it says it is still trying. Nothing else answers before its data does either: opening a list no longer flashes "This list no longer exists.", and a list card no longer reads "empty" before its count. Signing out now takes you to the home screen, so signing back in no longer opens settings first.

**150 more items, each filed in the aisle it is sold in** ([D-141]). Asian-supermarket staples were almost absent. Now there are sauces and pastes (fish, oyster, hoisin, sriracha, gochujang, miso, curry paste…), rice and noodle varieties, pak choi, Chinakohl, Koriander, tofu, kimchi, nori, gyoza, sake and more, plus Turkish, Middle-Eastern and Indian basics common in German cities (Fladenbrot, Ayran, Halloumi, Sucuk, Tahin) and US staples (ground beef, cheddar, salsa, BBQ sauce, hamburger buns). There is deliberately no "international" category: in an Asian market everything is international, and you still want frozen gyoza apart from sake and sushi rice. Fixes to existing entries: the alcohol aisle is now "Beer, Wine & Spirits"; "eggnog" had been translated as Eierlikör and is now two entries; Suppengrün moved to produce; frozen peas read "TK-Erbsen"; jam, honey, peanut butter and maple syrup moved to breakfast beside the chocolate spread. Items already on a list keep their aisle; the new vocabulary reaches existing installs at their next session after the server restarts.

**The typeahead ranks what is already on your list first** ([D-142]). Typing "Rahm" on a list that had bought "Sahne" suggested nothing: the dictionary entry was hidden because the row existed, and the row only matched its own name. Now everything already on the list (active, checked, or from your history) comes first, newest first, and matches through dictionary synonyms too; dictionary words you have never used follow. Within each group a name that starts with what you typed beats a synonym-only match, so "Rahm" offers Rahmspinat before Sahne. The bold part of a suggestion is now what matched: a synonym hit bolds nothing, instead of the wrong letters.

**Scanning finds pet food and non-food, and names products in your language** ([D-21]). Scans of cleaning products, pet food and other non-food goods, common among Aldi and Lidl house brands, used to end at "type the name": the lookup only asked Open Food Facts and Open Beauty Facts. It now also finds products in Open Pet Food Facts and Open Products Facts, still through the server so your device never contacts them, and an unknown barcode costs one request instead of two. Pet food lands in the pet aisle and beauty products in personal care, where their own tags had sometimes filed them under dairy or fish. A scanned item now carries the product's German and English names, and every member sees it in their own app language. An import listed in Italian reads "Nuss-Nougat-Creme" to a German household and "Hazelnut spread" to an English one, and typing either name finds it on the list. Renaming a scanned item sets one name for everyone. A product entered only under a German name is no longer reported as unknown, and the photo credit now names the whole Open Food Facts project. Items scanned before this update keep the one name they were created with.

**OIDC sign-in works, and the app keeps no email addresses** ([D-25], [D-153], [D-155], [D-156]). On instances with an OIDC login configured, "Continue with ‹provider›" failed every time in a real browser: the app took the provider's popup for closed the moment it reached the provider, and gave up. It now waits for the sign-in to finish, and while it is pending the button turns into "Cancel", for a popup you closed yourself. After "Link with ‹provider›" in settings, the passkeys that moved over to the provider account stopped working; they now keep signing in. A passkey moved by a link before this update stays broken: sign in with the provider and add a new passkey in settings. The link's explanation read "your undefined login" and now names the provider. The app no longer stores the email address the provider sends: nothing ever used it, and the planned email recovery is dropped. The recovery story is a second passkey, or the provider login where there is one. Deleting your last passkey is allowed exactly when the account can still sign in through the provider. Separately, on any instance, tapping "Sign out on this device" in the first moment after opening the app could sign you straight back in; it now stays signed out.

**Choose the logins an instance offers, and see only those** ([D-76]). Two new switches: `SHOPPINGLIST_PASSKEYS` (on by default) and `SHOPPINGLIST_OIDC` (off by default; `on` needs the provider variables). With passkeys off, an instance signs in through the OIDC provider only and no longer needs `EINKAUFSLISTE_RP_ID`. The auth screen and settings now show each login only while it is on: "Create account" disappears while `EINKAUFSLISTE_SIGNUP=closed` (it used to be offered and then refused), the passkey card disappears without passkeys, and a linked account's settings now say "Signed in with ‹name›". When a session expires, the sync chip signs back in with the login the device last used, so an OIDC-only account can re-authenticate there. **Upgrading with OIDC configured:** add `SHOPPINGLIST_OIDC=on`. The provider variables without it refuse the boot, rather than silently turning your login off, and `SHOPPINGLIST_OIDC=off` now really switches OIDC off, including a provider added through the dashboard. `EINKAUFSLISTE_SIGNUP` governs passkey signup only; who may sign in with OIDC is up to your provider. See the new "Choosing the login methods" section (now in docs/deploy-reference.md) before switching a login off: accounts that only have that login can no longer sign in, and the boot log counts them.

**Two ways sync could lose or double an item** ([D-175], [D-176]). If you checked an item off and removed it while offline, and someone else removed it first, the purchase was forgotten and the item never reached "Previous items". It is now remembered. The restore now joins the one already on the list, which keeps its values, and a value of yours that differed shows up in the usual conflict notice. **The shop tile's ⓘ shows only when there is more to see** ([D-83]). It now appears exactly when the tile hides something: a name or note that is cut off, or a scanned product's barcode. A tile whose text fits has no ⓘ, typed or scanned.

Every grey in the app used to carry the same sage tint as the buttons, so the whole app read as one sage wash, and in dark mode that tint became a green cast under a pale-mint button colour that outshone everything else on screen. ## v0.4.7: a hidden suggestion stays hidden, a vanished list says so, and a dead link is not hammered (2026-09)

Three sync fixes found by giving every basic feature, and the conflict notices, an end-to-end test for the first time.

**Hiding a suggestion offline sticks** ([D-137]). The account write for "Stop suggesting" swallowed every error, and every app start overwrote the local copy with the account record, so a name hidden with no signal came back at the next start, online or not, and a refused write did the same without a word. Every write also sent the device's whole list, erasing names another device had hidden since. Each change is now kept as a pending intent until the server confirms it and merged into the account's current list when it is delivered: after every change, at app start, on reconnect and after re-auth. Now the lost membership triggers a full sync at once, and the purge says "{name}" is no longer one of your lists. The wording is neutral, because the app cannot tell a deleted list from one this account left on another device. Reconnecting also always syncs fully now; a connection that dropped and came back within three seconds of the last sync used to skip it.

**A failed push waits for the retry** ([D-139]). A push that could not be delivered re-armed itself every 500ms for as long as the link was down, because the push's own bookkeeping write woke the watcher that schedules pushes. It now hands over to the existing 5-second retry.

## v0.4.6: a category you add finally syncs; a phone-sized item sheet, and taps that land where they were aimed (2026-09)

Findings from using the app on an iPhone, and one sync bug that had been there since categories shipped.

**Adding a category to a list never synced** ([D-08]). `addCategory` sent `slug: null`; `slug` is server-owned and outside the push allowlist, and one unknown field denies the whole op, so every added category came back `denied`/`field_unknown`. Since 2 Aug it has been reverted under the generic "could not be synchronised" toast; before that the denial was dropped silently and the row lived on only on the device that made it. The create now names only the writable fields. No layer had ever created a category end to end: the integration suite now drives the app's own `addCategory` against the real binary and expects the row on a second client, and the editor's component test checks the queued op against the contract's writable set.

## v0.3.1: the sync engine's stated invariants, made true; the shop tile stops measuring itself (2026-09)

No new features: this release answers the 2026-09-16 architecture audit and carries the maintainability sweep that was already in flight when it arrived. The audit's nine executable reproductions are promoted out of a `node_modules/.cache` directory one `pnpm install --force` from gone into the maintained suites (`$lib/sync/audit-repro.test.ts`, `src/integration/audit-repro.test.ts`, `e2e/tests/session-boundary.spec.ts`), each committed in its repaired form with a comment recording what it used to assert, since they are the only evidence that the defects below were real rather than read off the code.

**The gate printed FAIL and exited 0.** `scripts/gate.sh` marked a failed layer and moved on; the last statement standing was a false `if` with no `else`, which succeeds, so every automated consumer read "green" off a red run, and the audit found it only by injecting a failing layer into an isolated copy of the script. Failure is now accumulated and cashed in once after the summary (`set -e` is the wrong fix: running every layer and collecting all the evidence in one pass is what the script is for), and a FAILED `build-backend` SKIPs the two layers that would otherwise have reused the previous binary, which meant a green run against a build that did not contain the change under test. `scripts/gate-selftest.sh` guards it by faking `docker` to inject a failing layer into the REAL script: five cases including an all-green baseline, ~1s, no container, verified non-vacuous against the pre-fix script.

**Four client-side invariants the engine did not hold.** Settlement decided "edited in flight" from `queued_at` (a timestamp that says only THAT an op was touched, never which fields) and then re-based every field against the returned record, so a field the server had just REJECTED came back re-based onto the winning value and re-sent with it as `base`: first-committed-wins ([D-11]) became last-writer-wins one round-trip later, with the [§8.4] conflict toast already shown. `PendingOp.post_send` now records the sent/pending split as a TOUCH, deliberately not a value comparison [D-40]. The sync cycle checked `abandoned` once at entry and then made five awaited round-trips with a write after each, so a membership response held across `stop()` and a completed wipe still landed; and sign-out did not cross tabs at all: the other tab's in-memory SDK state went on rendering authenticated settings and refilled the tables the wipe had just emptied. `$lib/session` holds an epoch that `logout()` bumps first and broadcasts; the `pending_ops` drain moves inside the leadership callback, since mounting it outside made [§8.7]'s single-drainer guarantee false [D-109]. The snapshot purge ran only `if (memberships.length > 0)`, a guard against one specific bug whose cause was fixed at source, and it cost a user who loses their only membership the list forever; a shape check replaces it, so an HTML body throws at any length and the cycle aborts with nothing purged [D-28]. And SSE applied outside a transaction, licensed by a carve-out in `applyServerRecord`'s own contract. That was wrong, because what makes a read and write unsafe apart is a local write interleaving, which does not care how many rows the caller applies [D-40].

**A create that became a merge was stored nowhere [D-108].** [D-42]'s duplicate-delivery check asks `FindRecordById(op.RecordID)`, which can only match a create that became a ROW, so a retry after a lost-but-committed response looked like a brand-new create, the [D-29] merge ran a second time, and its re-activation UN-CHECKED a purchase another member had made in between. Ordinary flaky network, ordinary shopping; reproduced against the real backend. A server-only `merge_log` (migration 1778000010) keyed BY the discarded id makes the replay check a primary-key hit, answers `merged` with the survivor as it is NOW, and applies the re-activation exactly once; it is taken by the [§7.3] cascade with the list and swept at tombstoneGC's 180 days rather than inviteSweep's 30, since expiry re-exposes precisely the defect the log prevents. Second half of the same cause: [§8.2] coalescing means an offline add-then-check arrives as a create carrying `checked:true`, which `mergeInto` force-cleared for re-activation: a purchase dropped with an empty outbox and no [§8.4] notice, nothing the user could see or recover. Re-activation exists to rescue somebody ELSE's stale row and no longer overrules what this caller did to this row after adding it. *Rejected: the audit's alternative of simplifying create/merge so retries cannot reactivate at all.* It would make a smaller server, but re-activation is what a shopper expects when re-adding a staple they bought last week, and only its retry path was wrong. Known gap, recorded rather than fixed: an update still queued against a merged-away id is denied `row_missing` ([D-103]) rather than remapped to the survivor.

**The shop tile stops measuring itself [D-83].** Amends its shrink-before-truncate policy. Each tile ran a small layout engine of its own (measurement state, a ResizeObserver with a width latch, a double-animation-frame settling pass, a `document.fonts.ready` pass, and a name font stepped down 2px at a time to a 12px floor), and it was circular, since `shouldShowDoor` consumed the measured clamp flags while the door's reserved column changed the geometry being measured, which is why none of it could be deleted piecemeal. **The 'last bought' badge is retired; the date lives where it is asked for** ([D-18]). The badge's visibility was a five-term conjunction (unchecked AND bought AND ≥6h AND <7d AND on this one surface), of which four terms were invisible, so its silence meant nothing readable: a never-bought row and one bought 8 days ago rendered identically. The date moved to the two surfaces that ask the question: the previous-items row (with the absolute date as its accessible label) and the add bar's own suggestions. D-18's grace window and the badge-days env var deleted themselves with it; the wording ladder (days → weeks → months → years) serves a screen that keeps history forever.

**One done pile, drawn once, in the shop view** ([D-18]). The list view carried a "Recently checked" section although [§9.1] gives it no check-off control: an undo for a gesture it cannot perform, on the planning surface. The shop view's "Done" is the single recently-checked surface; "Previous items" starts where the shopping day ends.

**"Reset 'last bought' hints" tells the truth** ([D-100]). The route nulls `last_bought_at` on tombstones too, and after [D-18] that stamp IS a removed-bought row's history membership and GC exemption, so the reset deliberately forgets exactly those articles (they leave "Previous items" now and the 180-day sweep re-arms). Reviewed and kept: a remembered row is one the user removed on purpose, and the confirm is explicit, undoless and household-wide; the defect was the copy, which promised "items themselves stay" unscoped and now scopes it to articles **on the list**. An `items.remembered` boolean was designed and rejected: derivable from the stamp at every writer, it would exist only to represent the undated-history state this decided against.

**Settings loses the view row** ([D-101]). "Default view" wrote the same `meta.list_view` key the in-list control writes. It was a remote control for the current view, mislabelled as a default. Removed rather than relabelled or made dual-key: the control is one tap away in every list's app bar, and last-used-persisting already covers what a configured default would carry. First run still opens in Shopping; the shop's empty state now names the real tab ("Editing").

**The sync chip separates its one actionable state by shape, not hue** ([D-102]). Pending and expired shared amber; expired and offline shared the cloud-off glyph; the pending count lived only in `title=` (never rendered on touch) and `.sr-only`. Expired is now the app bar's only **filled** chip (solid destructive, key glyph), sharing no tint or glyph with any inert state; the pending count became the chip's glyph whenever N>0. Contrast pairs pinned in `design-tokens.test.ts` as before.

**Two safety nets and a placement repair.** The item detail sheet's "Remove" sat between the Note field and the Category picker: a delete button mid-form, with the form continuing below it; it is now the sheet's last element, the danger-at-the-foot idiom the settings screen uses. Category hide was the last mutation with no one-tap undo; it now raises the standard undo toast (a hidden category's items fall to Others, so the undo restores organization, not data, and a toast suffices where a confirm sheet would be ceremony). And the list row's scan-provenance mark graduates from an anonymous green dot to a **camera badge** on the aisle chip corner, mirroring ScanButton's own glyph, the very control that created the row.

Invisible in between: a render/sync/bundle perf pass ([D-95]), three add-bar correctness fixes (a stale combobox selection swallowed on fast fill+Enter, a committed add clobbering a newer typed name, un-suppress running on the hydrating snapshot instead of a fresh read), the type-aware lint tier repaired back to red-at-HEAD, and the suite's timing/CPU stability brought from incident to boring. [§6.10], [§9.1], [§12.1], [D-83], [D-18]–[D-102].

## v0.2.1: the second-passkey bug, plus barcode-scanner egress hardening (2026-09)

Fixes a bug present since the feature's first commit: `addPasskey()`'s `register/finish` request never carried the session's `Authorization` header (only `begin` did), so PocketBase, which resolves `e.Auth` from that header alone with no cookie fallback, saw every finish call as unauthenticated; the server's ownership check in `resolveRegistrationUser` then always refused with "session not found or expired" for every add-a-second-passkey attempt, on any device, regardless of OS or timing. The existing test suite only ever asserted the header on `begin`, never `finish`, which is how this shipped unnoticed; a regression test now covers both, and a repo-wide audit for the same failure class found no other instance (one test-coverage gap closed on `linkOidc()`, which was correct but untested). Alongside it: `webauthn_sessions` is now scoped by `(browser_id, type)` rather than `browser_id` alone, so a background conditional-mediation `login/begin` ([D-69]) can no longer delete an in-flight `registration` session for the same browser. Four items land in `item_dictionary` (non-alcoholic beer, dog waste bags, flea/tick treatment, diaper rash cream; `seed_version` 2→3). `docker-compose.yml` gains an opt-in, profile-gated `egress-proxy` Squid sidecar (its config inlined via `configs: content:`, no extra file to track) so a self-hoster who isolates the app container's network (a reasonable default, since almost nothing else it does needs outbound internet) doesn't silently break barcode scanning, which needs HTTPS to `world.openfoodfacts.org`/`openbeautyfacts.org`; the Hardening notes section (now in `docs/deploy-reference.md`) documents the requirement. [§5.4], [§9.2], [§14].
